# Export Flow 项目宪法

## 核心原则

### 一、AGENTS.md 是项目最高管理者

`AGENTS.md` 是项目最高级别的治理文件。本宪法只管理开发阶段规则，不得与
`AGENTS.md` 冲突。发现冲突时必须暂停工作，先修正本宪法使其符合 `AGENTS.md`。

### 二、先规格，后实现

中风险和高风险变更必须使用仓库的规格流程。开始实现前，功能必须具有经过评审的
`spec.md`、`plan.md` 和 `tasks.md`。生成的文档必须保留在 `specs/` 下的功能目录中，
并作为正式项目文档评审，不能视为一次性 AI 输出。

规格流程在确定进入功能实施准备后启动。产品与架构讨论、技术调查和纯文档整理可以先完成各自的文档评审，不因讨论内容可能涉及中高风险实现就自动生成规格。

规格评审必须由项目负责人明确给出批准结论。模型不得自行批准规格，也不得把自检、
自动化验证通过、生成规格的请求或需求中描述的目标交付物视为实施授权。未获得明确
批准时，只能继续修订规格和提出澄清问题，不得编写测试或生产代码。

每次准备规格时，`plan.md` 必须列出变更范围的目录、文件及函数设计草稿，包括前后端和
必要通用函数的名称、类型化参数、返回值、中文职责注释、简短流程与调用关系。详细清单
可以作为附属产物，由 `plan.md` 链接；不提前生成代码。执行细则见
[`specification.md`](../../docs/rules/specification.md)。

### 三、测试先行

实施行为变更必须先根据已批准的规格编写测试。实现前必须确认测试失败，或记录明确的测试
覆盖缺口。实现必须遵循“红-绿-重构”循环。不得为了让错误实现通过而削弱或改写测试。
规格审批只授权进入测试先行阶段。该阶段结束后必须在 `tasks.md` 中提交进度、执行结果、
预期失败证据和覆盖缺口，等待项目负责人再次明确批准；未获该批准不得编写生产代码。
测试阶段门禁通过要求测试环境正常、用例完整、新增行为有预期失败证据，覆盖缺口须明确
评审；不要求尚未实现的业务测试全部通过，环境故障也不能冒充预期业务失败。
测试准备的允许范围、阶段完成条件和进度字段见
[`testing.md`](../../docs/rules/testing.md)。
每条验收标准必须具有稳定的 `AC-xxx` 编号，并在任务清单中映射到一个或一组测试任务；
测试用例必须引用对应编号。实现前和提交前都必须检查验收标准到测试的映射没有遗漏。
每条成功标准必须具有稳定的 `SC-xxx` 编号，并映射到验证用例、运行环境和证据。
AC/SC 的唯一编号与定义维护在 `docs/product/acceptance-criteria.md`；其他文档引用具体
编号时必须提供可点击链接，不得复制定义。

AC 必须能够转化为可观察、可判定的行为断言。AC、实现任务和测试用例允许存在一对多、多对一和多对多关系，必须通过显式映射进行双向追踪；编号、映射表和完整性检查的具体执行规则以 `docs/rules/testing.md` 为准。

### 四、风险和追踪关系必须明确

进入实施准备的变更必须进行风险分级；无法确定时使用更高等级。需求、设计决策、任务、测试、
实现路径和 ADR 必须能够相互追踪。未确认的假设必须记录，不得默认为已确认事实。

### 五、变更必须可评审、可复现

开发产物必须足够明确，使其他贡献者可以复现开发流程。对本宪法、规格模板或共享规则
的修改必须经过评审，并记录验证结果。

## 工程领域规则分层

本宪法定义开发阶段的通用原则；`docs/rules/` 定义各工程领域的具体执行规则，二者
不是重复文档。前端、后端、测试、构建、脚本、容器和命名规则必须分别维护在对应的
`docs/rules/*.md` 中，并受本宪法和 `AGENTS.md` 约束。

领域规则文件只细化跨功能的技术栈、统一工程要求和质量门禁；单次功能的流程、状态、接口字段与运行参数归产品基线、已接受 ADR 或实施时的功能规格管理。领域规则不得降低本宪法规定的风险、评审、测试和追踪要求。
前端规则与后端规则属于必须遵守的实现细则，不得因为已存在本宪法而删除或合并。

## 开发约束

规格流程只负责需求澄清、技术计划、任务生成和实现任务编排。它不替代
项目在测试执行、格式化、静态检查、构建、打包、容器启动、部署、发布、监控或回滚方面
的规则和工具。

开发治理链为：

```text
AGENTS.md -> .specify/memory/constitution.md -> docs/rules/ -> specs/<feature>/ -> 源代码和测试
```

功能规格必须使用既定标准文件和名称，不得重新引入另一套核心规格格式。项目维护的
文档内容一律使用中文；标准文件名、代码符号和协议字段名可以保留英文。

## 开发流程

### 风险分级

- 低风险：纯文案、局部样式、无行为变化的重构、测试或文档修正。可以跳过规格流程，
  但仍必须遵守测试和评审规则。
- 中风险：新增接口或页面、业务规则变化、持久化字段变化、权限或性能变化、跨模块
  重构。必须使用核心规格流程。
- 高风险：认证授权、支付、隐私安全、数据迁移或删除、公共 API 破坏性变化、并发一致性
  或生产部署拓扑变化。必须使用核心规格流程，并增加 ADR、评审和回滚方案。

无法确定时必须使用更高风险等级。

### 中高风险顺序

1. 完成风险分级，阅读 `AGENTS.md`、本宪法和适用的 `docs/rules/`。
2. 根据 `spec-template.md` 创建或更新 `spec.md`。
3. 仍有重要歧义时，在规格中记录澄清结果，再根据 `plan-template.md` 编写 `plan.md`。
4. 根据 `tasks-template.md` 编写 `tasks.md`，提交项目负责人评审；未获得明确批准时暂停在本步骤。
5. 项目负责人明确批准 `spec.md`、`plan.md` 和 `tasks.md` 后，**必须先编写并运行测试**，确认测试失败或记录覆盖缺口；在此之前不得执行实现任务。
6. 在 `tasks.md` 中记录测试进度与证据，核对测试环境、用例完整性与预期失败证据等测试阶段门禁，提交项目负责人审批测试先行阶段；门禁未通过或未获得明确批准时暂停。审批记录须注明范围与版本，测试自动通过不能替代审批。
7. 测试先行阶段获批后，才允许在批准范围内编写生产代码。
8. 编写满足测试的最小实现，再进行重构。
9. 根据项目规则运行测试、静态检查、构建、打包和部署验证。
10. 按需更新受影响的 ADR 和索引。

## 治理

`AGENTS.md` 管理本宪法。修改时不得引入与 `AGENTS.md` 冲突的规则。


评审时，必须验证本宪法是否得到遵守。未决决策记录在 `docs/decisions-pending.md`；确认后按事项归属更新产品基线、ADR、本宪法或工程规则，不把单次功能决定塞进工程规则。
