# 任务：[功能名称]

**输入**：`specs/<feature-dir>/spec.md`、`plan.md` 及按需生成的附属产物。

**状态**：待项目负责人明确批准。中高风险功能的 `spec.md`、`plan.md` 和本文件全部获批前，不得编写测试或生产代码。

**组织方式**：按用户故事安排可执行任务。行为变更必须先编写并运行对应测试，确认失败或记录经批准的覆盖缺口，然后实施。构建、测试执行和容器验证遵守 `docs/rules/`，不由规格流程替代。

**编号来源**：AC/SC 的编号和完整定义只在 `docs/product/acceptance-criteria.md`；此处必须链接具体锚点，不复制定义。任务 ID 在本功能目录内唯一；测试用例 ID 在全项目唯一。测试名称、注释或元数据引用对应 AC，旁边的映射表提供可点击链接。

## 依赖与执行顺序

1. 项目负责人明确批准三份核心规格后才可启动测试任务。
2. 每项行为实现之前先运行对应测试，确认红灯或记录批准的缺口。
3. 每个故事完成后验证本故事的 AC/SC，再进入依赖它的故事。
4. 最后完成全量回归、性能/资源验证和产物检查；未达到门禁不得标记任务完成。
