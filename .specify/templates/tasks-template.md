# 任务：[功能名称]

**输入**：`specs/<feature-dir>/spec.md`、`plan.md` 及按需生成的附属产物。

**状态**：待项目负责人明确批准。中高风险功能的 `spec.md`、`plan.md` 和本文件全部获批前，不得编写测试或生产代码。

**组织方式**：按用户故事安排可执行任务。规格获批后先完成约定范围内的测试准备与执行，记录预期失败或覆盖缺口；测试先行阶段再次获项目负责人明确批准后才能实施生产代码。默认整个功能先测试再审批；分批须明确各批次并分别审批。构建、测试执行和容器验证遵守 `docs/rules/`，不由规格流程替代。

**编号来源**：AC/SC 的编号和完整定义只在 `docs/product/acceptance-criteria.md`；此处必须链接具体锚点，不复制定义。任务 ID 在本功能目录内唯一；测试用例 ID 在全项目唯一。测试名称、注释或元数据引用对应 AC，旁边的映射表提供可点击链接。

## 阶段 3：其他用户故事

按优先级复制“测试先行 → 测试阶段审批检查点 → 最小实现 → 验证”结构。默认先完成整个功能所有故事的测试先行任务，再统一提交测试阶段审批，不能按章节顺序提前实施第一个故事。分批须由项目负责人明确确认批次与范围，每批分别审批。跨故事依赖在此显式记录；不得为了并行而跳过共同前置任务。标记 `[P]` 的任务仅在不同文件且无依赖时并行。

## 依赖与执行顺序

1. 项目负责人明确批准三份核心规格后才可启动测试任务。
2. 先完成约定范围的测试先行任务，记录实际运行结果、预期失败或覆盖缺口及证据，不以环境故障冒充行为失败。
3. 提交测试先行阶段审批；未获得项目负责人明确批准不得编写正式工程骨架或其他生产代码。
4. 在批准范围内按依赖顺序实施；每个故事完成后验证其 AC/SC，保留红灯证据并追加绿灯与回归结果。
5. 新增行为或审批范围实质变化时更新设计与测试，重新确认受影响范围的审批。
6. 最后完成全量回归、性能/资源验证和产物检查；未达到门禁不得标记任务完成。
