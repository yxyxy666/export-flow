# 技术调查：统一删除的状态分流与清理边界

## 已确认事实

1. 当前任务状态为`PENDING`、`RUNNING`、`PAUSING`、`PAUSED`、`SUCCEEDED`、`FAILED`；任务动作由服务端`allowedActions`决定，前端目前没有删除动作。
2. 任务根记录被投递、执行、checkpoint、数据块、产物、暂停/继续和进度表以`ON DELETE RESTRICT`引用，不能直接删除根行。
3. RabbitMQ迟到消息和旧Worker必须通过任务权威状态裁决；数据库不可读时不能提前确认消息。
4. 文件存储按任务目录隔离，已有清理候选和引用保护机制；数据库事务不能包住长时间物理文件操作。
5. 任务活动版本和进度Outbox用于SSE列表更新，缓存不是权威事实源。

## 方案比较

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 直接物理删除`export_tasks`及级联表 | 不直接采用 | 现有外键为RESTRICT；必须先完成固定顺序的子表清理，并为迟到消息建立独立技术墓碑 |
| 仅前端隐藏任务 | 不采用 | 后端仍可下载、暂停、继续或被旧Worker写入，不满足删除语义 |
| 业务记录硬删除 + 独立技术墓碑 + 异步文件清理 | 采用 | 任务业务数据真正删除，同时保留最小消息身份和并发裁决能力；清理可重试 |
| 运行中立即标记FAILED后删除 | 不采用 | 删除不是执行失败，污染失败统计和重试语义，旧执行身份也可能继续写入 |

## 选定设计

统一接口只接受一次删除意图，服务端在任务行锁内根据当前状态选择`ACTIVE_STOP`或`TERMINAL_CLEANUP`。运行中先递增控制版本并建立删除屏障；安全停止后与终态任务共享清理作业。清理作业按固定锁序删除任务根行及所有业务子记录，再通过与任务表无外键依赖的最小技术墓碑处理迟到命令。

## 未决问题

- `PAUSED`是否允许删除；建议允许，但必须确认没有有效执行租约和未封存修复工作。
- 墓碑的长期保留期限；当前规格按永久保留任务身份处理，若要定期清理需另行设计消息过期/审计边界。
- 是否增加操作员审计主体；当前项目无用户认证模型，本期只保留操作ID和时间。
