# ADR-0007 Outbox 扫描与可靠补投原则

## 背景与现行边界

已有 ADR 明确任务与命令 Outbox 同事务提交，dispatcher 失败时保留记录并重试，但尚未细化何时扫描、如何避免重复领取，以及投递进程崩溃后由谁接手。本次正式固化补投架构原则，不提前生成规格、测试、表结构或生产代码。

受理边界与创建结果不明的处理分别追踪至 [`AC-050`](../product/acceptance-criteria.md#ac-050)、[`AC-051`](../product/acceptance-criteria.md#ac-051)；确认发送后的交付与幂等边界追踪至 [`AC-049`](../product/acceptance-criteria.md#ac-049)。新增自动失败与竞态处理追踪至 [`AC-052`](../product/acceptance-criteria.md#ac-052)、[`AC-053`](../product/acceptance-criteria.md#ac-053)，记录隔离、崩溃退避及队列保留分别追踪至 [`AC-054`](../product/acceptance-criteria.md#ac-054)、[`AC-055`](../product/acceptance-criteria.md#ac-055)、[`AC-056`](../product/acceptance-criteria.md#ac-056)。不新增用户可见状态，只为现有 `FAILED` 增加投递超时原因。

## 决策

以下为已接受的补投原则。投递阶段使用“待发送”“投递中”“已发送”描述逻辑，不据此预设数据库枚举；`SENT` 沿用已有 ADR 的已发送含义。

### 一、定期扫描持久化的到期记录

- dispatcher 启动或恢复后，以及后续扫描周期，读取已提交、未关闭、尚未标记 `SENT`、投递窗口未到期、已到下一次尝试时间且未被有效租约占用的记录。首次投递也走同一条路径，不依赖 HTTP 请求回调成功。
- 过期的投递领取权允许被重新取得；`SENT` 记录不在自动扫描范围内。不得通过扫描所有业务 `PENDING` 任务来猜测消息是否丢失。
- 扫描采用有界批次和并发，领取量不超过可立即处理的容量，按到期时间及稳定次序推进，避免预先囤积大量记录或使旧记录长期饥饿。
- 周期扫描是补投兜底机制，调度依据持久化，不只依赖一次性的内存定时器或启动通知；它不同于前端任务状态轮询，不改变产品的 SSE-only 要求。

### 二、短事务取得短时领取租约

- 在 MySQL 短事务中以条件更新取得每条记录的投递权，保存领取者、租约截止时间和每次领取都会更换的凭据；事务提交并确认领取成功后才能发送。具体锁策略、隔离级别和 SQL 留待规格验证。
- 租约判断、到期调度和条件回写使用统一的数据库时间依据，不依赖不同实例的墙上时间。发送及等待 broker 结果期间不得持有数据库事务或行锁。
- 租约覆盖单次有界投递的总时间预算；开始发送前核对领取权仍有效。进程崩溃后，记录不删除，其他 dispatcher 可在租约过期后条件接手。
- 成功标记、失败回写和释放领取权均核对当前凭据、未过期租约及投递阶段。旧进程或迟到回调不得覆盖新领取者的状态；条件更新不成功时停止回写并核对记录。
- 租约只能保护数据库领取与回写，无法撤回已发送到 RabbitMQ 的消息；接管窗口仍可能重复发送，不能宣称恰好一次投递。

### 三、确认接收且正确路由后标记已发送

- 每次发布关联当前领取凭据与本次发布结果。仅当 RabbitMQ 发布确认和正确路由结果都满足要求，且当前投递权仍有效时，才条件标记 `SENT`。
- 明确发布失败、不可路由、确认超时或连接中断均不能标记 `SENT`。无路由消息可能仍获得发布确认，不能把单独的 ACK 或发送函数返回当作成功；具体路由检查机制及持久化拓扑须在 RabbitMQ 方案中批准。
- 已确认接收但 MySQL 标记失败时，若仍持有有效领取权，优先重试成功标记，而不是立即再次发消息。进程重启或接管后无法证明原发布结果时，允许重发同一命令。
- Outbox 标记结果不明时先回读；已经 `SENT` 就停止，未能确认时保留记录并交由后续核对或接管。不得因自身回写异常覆盖已经提交的 `SENT`。

### 四、持久化退避并保留失败证据

- 采用有上限的指数退避与抖动，持久化下一次尝试时间、尝试记录和脱敏错误分类；扫描只领取到期记录，重启后沿用已保存的调度依据。
- 领取事务同时持久化本次尝试序号、开始时间和崩溃接管后的退避依据，不把这些信息推迟到失败回调才保存。序号表示投递尝试预约，不证明消息已发送；接管时继续推进尝试历史，不重置为首次尝试。无失败回写时也须同时满足租约已过期和退避已到期，不能仅因领取权到期立即无限重试。
- 单次尝试的完整时间预算包含发布、确认及状态回写；普通待执行任务的尝试预算和调度均受剩余投递窗口限制。退避或租约不能延长总截止时间；到期判定不受下一次重试时间约束。
- 尝试记录用于诊断投递过程，不等同于 Worker 执行次数，也不作为未经批准的任务失败条件。租约过期且发布结果不明的接管也应保留诊断，避免反复立即重试形成故障风暴。
- 暂时不可用、不可路由与配置错误分别可诊断；持续失败触发受控告警，不丢弃原记录。不以尝试次数决定业务失败，而按第十节的总窗口自动终止未发送、未开工的任务，无需人工批准。
- MQ、MySQL 和 dispatcher 在窗口内恢复且持续可用时，到期记录继续被处理；超过窗口并已自动失败的记录不因 MQ 恢复而复活。

### 五、补投保持同一命令身份，消费端幂等

- 补投沿用同一事件身份、任务 ID 和消息版本，不创建新任务、改变范围快照或生成新业务重试请求；事件身份与领取凭据不同，前者不变，后者每次领取更换。
- 发布成功后、标记 `SENT` 前的崩溃窗口允许重复消息。消费端继续按已接受 ADR 的 MySQL 条件认领与终态检查处理，不因消息重复生成第二份文件。
- 原 Outbox 已为 `SENT` 时，不因任务仍为 `PENDING` 而自动重置或新建补投记录；已接收消息的排队与未确认消息重交付仍由 RabbitMQ 负责。异常数据修复须另行核对和评审。

### 六、区分 dispatcher 租约与 Worker 租约、心跳

- 本文的领取租约保护的是一次短时发布，不是导出文件的长期执行权。单次发布采用明确超时，不默认给 dispatcher 增加周期心跳或无限续租；如未来需要续租，须单独评审预算、误判和回写竞态。
- Worker 已提交 `RUNNING` 后崩溃的租约、心跳、接管与旧执行者隔离仍属于[待确认决策](../decisions-pending.md)，不因本 ADR 的补投设计而视为已解决。
- dispatcher 停止时先停止新领取；有界等待当前投递并持久化可确认的结果。确认未开始发送的记录可条件释放；无法确认发布结果的记录保留，交由租约到期恢复，不能提前标记 `SENT`。

### 七、用户查询与运行可观测性

- “事务提交成功、发送失败且尚未认领”时，在投递窗口内用户可查到原任务且任务保持待执行；到期由第十节自动失败规则处理。dispatcher 不把投递阶段、错误堆栈或领取者暴露为新增业务状态。
- 发送结果不明不代表 Worker 尚未开工，用户查询始终以 MySQL 任务状态为准，不因 Outbox 重试把 `RUNNING` 或终态回退为 `PENDING`。
- 监控待发送数量、最老记录年龄、到期但未处理的积压、发布失败分类、过期领取、回写失败及 dispatcher 健康；日志关联事件与任务，但不记录客户信息、完整载荷或密钥。
- 未发送和因超时关闭的记录保留供核对，不以停止重试代替删除。已发送/关闭记录和尝试历史保留不自动清理，告警阈值见[决策记录](../../specs/002-order-management/decision-record.md#文件及执行参数)；超时原因、用户文案和终止规则按第十节执行。

### 八、已确认消息的可靠保留

- 任务命令只允许进入获批的目标任务队列，采用持久队列与持久消息，并按确认协议完成可靠存储交接。具体队列类型与拓扑在规格中验证；路由到其他队列不算该命令交付成功。
- 目标任务队列不得配置消息 TTL、自动删除、队列到期删除或丢弃旧消息的溢出策略；运行中策略变更不得静默引入这些行为。若设置容量上限，采用拒绝新发布并使生产者获得可判失败结果的策略，不能通过淘汰已确认消息释放空间。
- 按锁定的 RabbitMQ 版本核对重交付次数上限等默认策略；未批准可靠转移和任务处置前，不允许因达到重投上限静默丢弃已确认消息，不能只检查显式配置而忽略 broker 默认行为。
- 不以死信替代正常执行。未来如启用过期、淘汰或死信转移，须另行批准可靠转移与后续任务处置；当前不把已 `SENT` 消息的丢失纳入普通补投超时。
- 启动和运行监测核对目标队列及有效策略；不满足保留要求时阻止新命令被错误标记 `SENT` 并告警。灾难性数据损坏或队列被误删不在正常可靠保留保证内，须另行恢复，不靠任务等待时间猜测丢失。

### 九、单条记录故障隔离

- 序列化错误、消息版本不支持、不可路由等单条错误只影响该记录的结果和调度，不回滚其他记录的成功标记，也不中断整批或整个扫描循环。
- 保留坏记录的事件身份、脱敏错误与到期安排，继续处理其他记录；超时后仍按第十节收口。不默认删除坏记录、永久跳过它或让用户承担人工排障。
- MySQL 不可用、MQ 连接级故障等共享依赖错误允许有界停止当前批次并退避；它们与单条载荷错误分开诊断，恢复后扫描继续。

### 十、十分钟窗口内无法确认投递则自动失败

- 本项目采用固定的 **10 分钟总投递窗口**，不是每次重试各等十分钟，也不按重试次数终止。任务与 Outbox 创建事务中用数据库时间持久化受理时间及其加十分钟的截止时间，只有提交记录才参与扫描；创建事务必须保持短时。截止时间不可被重试、实例重启、租约接管或部署重新计算。
- 十分钟是本项目授权确定的等待预算：给临时依赖故障留下恢复与多次退避的机会，同时避免用户无限等待；它是产品取舍，不是行业标准或已测性能结论。将来调整须同步产品基线与 ADR，不能静默更改已有任务的期限。
- 后端自动超时扫描器在启动恢复时检查，并在健康运行时每 **5 秒**启动有界到期扫描；不依赖 MQ 发布回调、投递租约到期或某条记录的下一次尝试时间。可与 dispatcher 同服务部署，但独立于其单次发布循环，MQ 不可用时仍能使用 MySQL 判定。多实例使用数据库裁决，不需人工接单。
- 到期失败只针对原任务仍为 `PENDING`、原命令未 `SENT` 且未关闭的记录。扫描器在同一短事务中条件推进任务至 `FAILED`，写入结束时间与错误码 `TASK_DISPATCH_TIMEOUT`，关闭原 Outbox 的自动投递并撤销领取权。失败与关闭必须一起提交，不能留下“用户看到失败，原命令仍可正常发送”的数据库状态。
- Worker 认领、dispatcher 成功标记和超时失败使用同一任务/Outbox 的串行化裁决及一致锁顺序；取得裁决权后读取数据库当前时间。对于未发送且待执行的任务，期限内成功裁决允许认领或标记 `SENT`，达到截止时间后不再授予这些权利。具体事务与 SQL 由规格验证，不能用各实例的墙上时间或一次无锁预查询决定胜负。
- 已 `SENT` 的任务排除在本超时范围外，即使还在排队也不判失败；Worker 已成功认领或任务已终态时，也不得按投递超时改为失败。这类未开工投递判定不代替排队超时或 Worker 执行超时。期限内已开工但 Outbox 尚未标记的记录，可核对确认结果，不再被该扫描器误判失败。
- 到期核对发现任务已开工或已终态而原 Outbox 未 `SENT` 时，停止补发该创建命令并保留诊断；有可靠发布确认依据才标记 `SENT`，否则以“权威任务状态证明无需再发送”的原因关闭原命令，不伪造发布确认、不改变业务状态，也不替代 Worker 执行恢复。
- 超时失败提交后，旧 dispatcher 的确认或回写不得把已关闭记录改为 `SENT` 或重新打开。跨 MySQL/MQ 的在途消息仍可能到达；Worker 核对到已提交的失败终态后只确认消费，不生成文件、不改变原失败结果。MySQL 不可读或终态未确认时不能擅自 ACK。
- 发布结果不明也可能达到截止时间；该失败表示“规定时间内未完成可确认的投递且尚未开工”，不声称 MQ 从未接收过消息。已确认但未持久标记的命令可能被关闭；这项有界等待取舍由本 ADR 明确接受，并以数据库执行权防止随后执行旧任务。
- 用户错误摘要为“任务投递超时，未开始执行。请重试或重新创建任务。”；失败沿用现有终态通知链路和快照查询，不引入前端轮询。用户执行现有失败重试或重新提交时，创建新任务及新 Outbox，使用新提交幂等标识；原失败任务保留。同一原标识只找回原失败任务，不偷偷新建。
- 数据库或整个后台服务不可用时，不能承诺在截止时刻写入失败；恢复后优先处理到期记录，不能重新授予已过期且未确认发送的任务执行权。五秒是扫描启动周期，不是积压、资源不足或数据库不可用情况下的终态可见硬保证。

## 被否决的替代方案与理由

| 对应决策 | 替代方案 | 否决理由 |
| --- | --- | --- |
| 定期扫描 | 只在 HTTP 提交后或内存通知中发送 | 请求结束、通知丢失或进程崩溃后缺少持久补投入口 |
| 条件领取与租约 | 普通查询后直接发送，或永久标记投递中 | 前者不能裁决并发，后者可能让崩溃记录永远无法接手 |
| 短事务与有界发布 | 持有数据库行锁等待 MQ，或无限续租 | 外部故障占用数据库资源，卡住的投递可能长期阻止接管 |
| 双重成功判断 | 发送函数返回或单独收到发布 ACK 就标记 `SENT` | 不能证明命令正确路由，可能失去正常补投机会 |
| 持久退避 | 每轮立即重试所有失败记录，或只记内存计时 | 容易产生故障风暴，重启后丢失退避依据 |
| 同一命令幂等 | 补投时新建任务，或把租约当作恰好一次保证 | 破坏原任务追踪，且租约不能消除跨 MySQL/MQ 的重复窗口 |
| 两类租约分离 | 用 dispatcher 租约替代 Worker 执行心跳 | 保护的阶段不同，无法恢复已经失去执行者的 `RUNNING` 任务 |
| 权威状态与监控 | 投递失败就报创建失败，或因排队过久自动补投、失败 | 混淆受理、交付和执行，违反当前已接受边界 |
| 队列可靠保留 | 用 TTL、淘汰旧消息或自动删队列控制积压 | 已确认消息可能消失，普通 Outbox 扫描已不负责补投 |
| 崩溃退避 | 只在失败回调记录尝试，接管时重置重试次数 | 崩溃可绕过退避，形成租约到期后的反复立即尝试 |
| 单条故障隔离 | 一条坏记录终止整批，或静默删除它 | 正常任务可能被阻塞，或丢失可追踪的处理结果 |
| 自动超时收口 | 永久等待人工处置，或仅按固定尝试次数失败 | 不符合自动化要求，尝试次数也无法稳定约束用户等待 |
| 条件终止与关闭 | 到点直接改任务失败，不核对认领和已发送状态 | 可能把正在执行或正常排队的任务误判失败，并让迟到命令继续执行 |

## 失败窗口与责任

| 失败窗口 | 持久记录与用户可见结果 | 恢复责任 |
| --- | --- | --- |
| 创建事务明确回滚 | 无已提交任务及该命令，不返回创建成功 | 请求端按已有创建契约处理，不由 dispatcher 伪造任务 |
| 事务提交后、首次扫描前进程退出 | 任务可查，尚未认领时为 `PENDING`；Outbox 待发送 | 恢复后的 dispatcher 扫描 |
| 领取提交后、发布前进程退出 | 原任务与 Outbox 保留，领取权会到期 | 其他或恢复后的 dispatcher 条件接管 |
| 发布失败或结果不明 | Outbox 不标记 `SENT`；用户看到 MySQL 中的实际任务状态 | 有效领取者保存退避，或租约过期后接管；结果不明时容许重复 |
| 已确认发布、标记前退出 | MQ 可能已有命令，任务也可能已开工；Outbox 未确认发送 | dispatcher 补发同一命令，Worker 幂等处理 |
| 已标记 `SENT`，任务仍待执行 | 命令不进入自动补投扫描，用户仍看到待执行 | RabbitMQ 负责交付；异常丢失另行受控修复 |
| Worker 已认领后退出 | MySQL 可能仍为 `RUNNING` | 另行批准的执行恢复方案，不属于本 ADR |
| 总窗口到期且未确认发送、未开工 | 任务与原 Outbox 同事务失败和关闭；记录保留 | 自动超时扫描器，无需人工批准 |
| 失败提交后迟到消息或发布确认到达 | 原任务仍失败、Outbox 仍关闭 | dispatcher 禁止旧回写，Worker 核对终态后 ACK，不生成文件 |
| 期限内已确认发送或认领，与超时并发 | 按共同数据库裁决结果排除正常排队或执行 | dispatcher、Worker 与扫描器使用一致事务门禁 |

## 验证与实施门禁

补投验证关联已确认 [`SC-010`](../product/acceptance-criteria.md#sc-010)，其审批状态不因本文原则获确认而改变。未来获批规格须将已有 AC/SC 与正式测试、运行环境和证据显式映射；新增可观察断言先在验收基线维护编号，不在本文另建标准。

进入获批实施阶段后，至少在隔离的真实 MySQL/RabbitMQ 上验证以下窗口；现在只列验证要求，不编写或声称已执行测试：

1. MQ 不可用时提交成功、原任务可查、Outbox 保留；恢复 MQ 且不重新提交用户请求，原任务最终被执行。
2. 创建回滚没有可投递记录；提交结果不明时按原提交标识核对，不产生第二个任务。
3. dispatcher 在领取前、领取后发布前、发布后标记前及标记后退出，恢复结果均符合失败窗口表。
4. 多 dispatcher 争抢同一记录，过期领取被接管，旧凭据及迟到回调不能覆盖新状态；模拟数据库回写结果不明并核对已提交状态。
5. 无路由、发布 NACK、确认超时和连接中断不产生错误的 `SENT`；消息结果不明时允许重投但不重复业务结果。
6. 退避和到期时间跨重启保留，扫描批次与并发受限；崩溃在发布失败回写前也不重置尝试历史或绕过退避，单条坏记录不阻断其他记录。
7. 已 `SENT` 的长期待执行任务不被扫描补投；dispatcher 租约测试不得被当作 Worker 崩溃恢复已验证的证据。
8. 核对队列有效 TTL、自动删除与溢出策略；broker 重启保留已确认命令，容量上限拒绝新发布但不丢旧消息，策略不合规不能误标 `SENT`。
9. 用可控时钟覆盖截止时间之前、恰好到期及之后；MQ 持续断开时无需人工操作即关闭原命令并提交失败，新建任务与原记录独立。
10. 覆盖失败、认领与发布确认的并发次序，迟到确认、已关闭后重复消息、原幂等标识重放，以及数据库/扫描器中断后的到期恢复；验证不误伤已 `SENT` 或已 `RUNNING` 的任务。
