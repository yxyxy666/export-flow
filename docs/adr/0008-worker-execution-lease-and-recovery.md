# ADR-0008 Worker 执行权、用户暂停、断点恢复与竞态隔离

- 状态：提议，待项目负责人评审；不是已接受决策，不构成规格、测试或实现授权
- 日期：2026-10-03
- 适用范围：Worker 接收任务命令、取得执行权、用户暂停与恢复、持久化断点、异常中断后的接管及多 Worker 竞态
- 上游：[产品需求](../product/order-export-prd.md)、[验收基线](../product/acceptance-criteria.md)、[`ADR-0003`](0003-application-stack-and-local-runtime.md)、[`ADR-0004`](0004-rabbitmq-task-queue.md)、[`ADR-0006`](0006-broker-owned-pending-delivery.md)、[`ADR-0007`](0007-outbox-dispatch-retry.md)

## 背景与评审边界

现有决策已确定 RabbitMQ 负责已发送命令的交付，MySQL 负责业务状态和开工裁决，消费确认留到终态提交或权威核对证明无需处理之后。本提案补充执行权、暂停控制和断点生命周期，不改写原创建命令的补投职责。

项目负责人本轮提出的需求方向是：区分用户暂停与异常中断，恢复优先断点续写，无法继续才从头重建；续写仍属于原任务。原提案“本期总是从头重建”的建议已被替换。用户暂停是现有产品状态之外的新增能力，相关产品与验收定义、暂停确认边界和恢复命令架构仍须评审，不把本次需求描述视为整份 ADR 或实施规格已经获批。

导出中间数据以任务专属临时文件承载，不将完整任务内容保留在进程内存中；执行权、暂停意图、断点清单和文件引用保存在 MySQL。具体内存缓冲、读写和落盘策略属于后续规格，本轮不展开。

本次只讨论架构，不生成功能规格、表结构、消息字段、SQL 或代码。未来实施涉及并发一致性，按高风险变更处理，须先批准架构与相关产品口径，再完成并明确审批规格、计划、任务和回滚方案。

已有边界追踪至 [`AC-010`](../product/acceptance-criteria.md#ac-010)、[`AC-012`](../product/acceptance-criteria.md#ac-012)、[`AC-013`](../product/acceptance-criteria.md#ac-013)、[`AC-016`](../product/acceptance-criteria.md#ac-016)、[`AC-049`](../product/acceptance-criteria.md#ac-049)、[`AC-053`](../product/acceptance-criteria.md#ac-053)。用户暂停与恢复、断点优先、完整重建回退、自动恢复及恢复耗尽的新增验收定义，须在评审后维护到唯一验收基线，不在本文件另立编号或定义。

## 候选架构总览

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| RabbitMQ | 竞争消费者交付任务命令，保管未确认投递，按获批协议重交付 | 不决定哪一个 Worker 拥有业务执行权，不裁决任务成功或失败 |
| MySQL | 保存任务、用户控制意图、控制版本、执行锁、隔离代次、断点清单及结果引用，裁决认领、续租、暂停、接管与终态 | 不按运行时间扫描并重新发布已发送创建命令 |
| Worker 执行器 | 持有效执行权读取只读订单，持久化不可变数据块和断点，装配独立 Excel，响应暂停 | 不覆盖其他尝试产物，不在失权或暂停生效后推进业务状态 |
| 消费监督器 | 独立于文件生成检查本地交付、认领与执行健康，协调停止、通道关闭和结果核对 | 不仅凭时间把正常排队任务判失败，不绕过 MySQL 发放执行权 |
| 文件存储 | 在受控落盘临时目录保存尝试隔离的中间数据块、生成中的 Excel 及就绪产物 | 不把内存缓冲当文件存储，不通过文件名或文件存在自行宣布断点提交或业务成功 |

执行锁是 MySQL 持久化、有有效期和持有者身份的业务执行权，不是在整个导出期间持有数据库行锁。它与 dispatcher 短时投递租约是不同的权利和时钟。Redis 不参与抢任务、续租或执行权裁决。

## 一、从队列领取消息与认领任务分开

- Worker 使用 RabbitMQ 竞争消费者接收命令，不通过扫描 MySQL 的 `PENDING` 任务抢工作。接收量受本实例实际执行容量约束，不能先大量预取再长时间等待认领。
- 收到消息后保持手动未确认状态，按任务 ID 读取 MySQL 权威记录，再用短事务裁决。`PENDING` 的首次认领仍遵守 [`ADR-0007`](0007-outbox-dispatch-retry.md) 与 dispatcher、投递超时扫描器的共同裁决边界；不能绕过截止时间直接开工。
- 首次认领将任务推进为 `RUNNING`，同时建立执行尝试、执行者身份、有界租约和新的隔离代次。只有确认该事务提交且自己仍持有效执行权后，才能生成文件。
- 认领提交结果不明时，以自己的执行身份回读核对；无法证明取得有效权利时不得开始，也不得 ACK。生成文件期间不持有数据库事务或行锁。
- 建议将一个执行槽的在途交付放在可独立关闭的消费通道中，限制故障关闭的影响范围；不为此要求每个任务建立独立 TCP 连接。连接级故障仍可能影响多个槽，所有受影响尝试各自按失权流程处理。

### 收到消息时的状态分支

| MySQL 权威情况 | 候选处理原则 |
| --- | --- |
| `PENDING` 且允许开工 | 条件首次认领，成功者执行，失败者重新核对 |
| `RUNNING` 且租约有效 | 不执行、不仅凭其他 Worker 正在执行就 ACK；监督器保留有界等待并重新核对终态或租约，避免立即 NACK/requeue 热循环 |
| 允许运行、已开工且租约过期 | 按恢复预算和退避条件争取接管，取得执行权后校验并恢复断点；不能直接开始生成 |
| 用户要求暂停但尚未生效 | 不授权新执行者；有效持有者收尾断点并停止，失联时等租约过期后核对并登记暂停 |
| 已确认暂停或消息控制版本已失效 | 当前消息不能驱动执行；确认持久化控制状态及后续恢复责任后才能 ACK，不能自动接管 |
| 已提交终态 | 不再生成文件，确认当前通道上的本次投递 |
| MySQL 不可用或结果无法核对 | 不授予执行权、不猜测终态、不 ACK；有界等待后受控关闭通道，由 RabbitMQ 恢复交付 |
| 无法解析、未知版本、任务不存在或权威记录不一致 | 进入另行评审的异常消息隔离流程，不默认丢弃、立即 ACK 或无限热重投 |

等待和核对也占用受控交付容量，不占用长时间生成线程。相关内部监督不是前端任务轮询，不改变 SSE-only 要求。

## 二、执行锁采用 MySQL 租约与单调隔离代次

- 每个任务在 MySQL 中至多有一个当前有效执行者。每次首次执行、显式恢复或异常接管都产生更大的隔离代次，同时记录本次执行身份；任务 ID 和原创建命令身份保持不变，显式恢复使用独立授权命令。
- 认领、续租、接管、暂停和恢复授权通过短事务锁定或条件更新同一权威任务记录，只有一个竞争者能提交有效执行权。事务结束后释放数据库锁，长时间工作由持久化租约保护，不能一直持有行锁生成文件。
- 租约判断、续租、接管和终态提交以数据库时间和串行化裁决为准，不用机器墙上时间或“我先收到了消息”决定胜负。过期租约不能通过迟到心跳复活。
- 每次续租、断点与进度写入、产物就绪登记、失败或成功提交，都验证当前执行身份、隔离代次、控制状态和有效租约。暂停收尾只允许提交受控安全边界，不能继续领取后续数据块或抢先成功。不能只在开工时检查一次，也不能只凭 Worker 名称更新。
- Redis 更新和 SSE 通知只能基于已经提交的 MySQL 变化；跨尝试的版本必须能识别迟到更新，不能让旧代次缓存覆盖新尝试或终态。可靠通知通道仍按 [`ADR-0005`](0005-backend-stack-and-progress-cache.md) 单独评审。
- 心跳用于维持仍可执行的尝试，但不允许无限执行。每次尝试还必须有独立的有界执行期限；文件生成长期卡住时，即使监督线程仍活着，也不能无限续租。
- 续租失败或结果不明时，Worker 必须在无法证明租约仍有效之前停止进一步业务副作用并核对；不能依靠本地记忆继续写进度或提交结果。
- 失权 Worker 停止执行并仅释放自己可以安全释放的资源。接管后旧 Worker 的迟到心跳、进度和结果被 MySQL 拒绝；短暂重复读取或生成可能存在，但只有一个执行身份能提交权威结果。

本提案保证的是受隔离的执行权与唯一有效结果，不宣称物理计算、临时文件生成或消息投递恰好一次。

## 三、用户暂停与异常中断是两条路径

以下“请求暂停”“暂停生效”“请求恢复”是逻辑阶段，不提前确定数据库枚举、API 或按钮。本轮讨论已开工任务的暂停；排队期间暂停涉及原创建命令的投递窗口，须另行评审，不默许改变 [`ADR-0007`](0007-outbox-dispatch-retry.md)。

### 用户暂停：保留断点，不自动接管

- 暂停请求先在 MySQL 持久化用户意图和控制版本，立即阻止新的认领、接管和后续数据块启动，不只在前端改变显示。
- 持有者在受控安全边界停止：提交已经完整持久化的数据块和断点，或丢弃尚未完成的块，然后停止写入和续租。暂停不是异常失败，也不消耗异常恢复预算。
- 只有执行器已确认停止，或原租约过期且数据库已废止旧执行身份后，才能在 MySQL 登记暂停生效。不能用户刚点击就宣称已经停止，也不能先释放执行锁再让旧线程继续提交。
- 暂停意图存在时，即使原 Worker 崩溃、消息被重交付，也只核对并完成暂停，不自动接管继续生成。保留最后一个可信断点；尚未完成的块不算已经保存。
- 暂停生效事务保存可用断点并废止旧执行权后，建议确认本轮消息，因为权威控制状态证明该命令当前无需执行。该非终态确认前提是恢复入口具有下述持久化交接，不能在暂停请求尚未核对时提前 ACK。

### 用户恢复：原任务的新执行授权

- 用户明确恢复后，在同一 MySQL 事务更新原任务的控制状态，并写入本次恢复授权的 Outbox。任务 ID、导出范围、字段和原提交幂等结果不变；这是同一任务的新命令，不是复制任务，也不是重发原 `SENT` 创建命令。
- 本次恢复命令通过既有 dispatcher 与 RabbitMQ 可靠交付。它具有独立的授权身份和控制版本，不能直接复用或重置原创建 Outbox；发布与补投机制可复用，投递时限和失败口径仍需单独审批，不自动套用创建命令的十分钟窗口。
- 多次点击恢复只产生一次有效授权；暂停尚未生效时，不提前排入另一个可执行命令。过期的创建或恢复消息不能越过新暂停意图，迟到的暂停收尾也不能覆盖已提交的新控制状态。
- Worker 收到有效恢复命令后仍先取得 MySQL 执行锁，再核对断点续写。恢复可以换 Worker，但必须继续原任务，并先确认旧执行资格已失效。

这一暂停确认及显式恢复命令方案仍为待评审扩展；正式接受时须同步产品状态、验收基线及 [`ADR-0004`](0004-rabbitmq-task-queue.md)、[`ADR-0006`](0006-broker-owned-pending-delivery.md) 的消息确认与命令职责描述，不能借“无需处理”静默扩展现有实现授权。

## 四、异常恢复优先断点，无法继续才重新开始

### 中断的职责边界

- 进程退出、连接中断或执行槽关闭时，未确认命令由 RabbitMQ 按获批协议重交付；MySQL 中的 `RUNNING` 不自动回退为 `PENDING`，也不重新建立创建 Outbox。
- Worker 一旦得知承载本次交付的消费通道已失效或消费者被取消，就停止本地尝试和续租，核对已提交结果；不能自动恢复连接后沿用旧投递标识 ACK。新交付是新的本地处理入口，仍须核对 MySQL。
- 心跳停止后，其他 Worker 只能在数据库租约过期且恢复条件满足时接管，不能仅凭收到重交付消息立即抢走有效执行权。
- 连接存活但认领或生成卡住时，独立消费监督器先区分阶段，要求停止该槽、停止续租并有界关闭对应通道。无法确认旧执行器停止时，不立即释放有效租约；等待过期后用新代次隔离旧执行器。
- 监督器本身停滞时，RabbitMQ 的连接故障检测与消费确认超时作为交付侧兜底。实际版本和队列类型必须支持并验证所需行为，不能只假设超时一定关闭通道。确认预算需覆盖健康长任务及受控恢复等待，不能直接采用短认领阈值。

### 可恢复中断与完整重建回退

**恢复顺序调整为：核对终态或就绪产物 → 校验最后一个可信断点并继续 → 断点确实无法继续时，在原任务内从头重建。** 用户暂停等待显式恢复，异常中断才按预算自动接管；两者不能混用。

恢复判断不能只看“已处理条数”。需要能够证明断点引用的前序数据块完整、顺序连续、与任务配置兼容且可访问。依赖暂时不可读时先等待或重试核对，不立刻宣布断点损坏并从头重建；校验结果不明时也不能跳过前序数据。

- 自动接管不创建新的业务任务，不改变原范围、字段或原提交幂等结果。执行尝试可以增加；用户对已失败任务点击重试，仍按产品基线创建新任务。
- 恢复次数、有界尝试期限和退避共同约束自动恢复，不能无限重做。接管时在 MySQL 中原子裁决预算并记录诊断，不把 broker 重交付次数直接当作业务执行次数。
- 建议可恢复中断走有界接管；已确认的不可恢复生成错误，或恢复预算耗尽时，由有裁决权的事务提交 `FAILED`、错误摘要并废止执行权，再确认消费。执行失败分类及此自动失败原则均属于本次待批准内容，不沿用投递超时原因。
- 异常自动恢复不把已开工任务伪装成首次 `PENDING`；用户暂停需要产品状态扩展。对外进度应以已提交且仍有效的断点为依据；完整重建时旧断点失效后的进度口径须审批，不能自行回退或用高水位冒充有效断点。
- broker 的重交付限制和死信策略不得先于应用恢复裁决静默丢弃未终态命令。若目标队列有强制限制，必须同时批准可靠隔离与恢复路径；本提案不默认增加重试队列或恢复发布器。

## 五、断点由持久化数据块和 MySQL 清单组成

建议将“读订单并保存导出数据”与“装配最终 Excel”分成两个阶段，继续使用 Apache POI SXSSF 生成最终 `.xlsx`，不将其进程内状态或私有临时文件当成可跨进程恢复的协议。

### 数据阶段：分块提交真正可复用的工作

- 按任务固定范围、有序字段和稳定订单顺序读取，将每块完整导出行流式写入受控落盘临时目录下的独立文件，不以进程内列表、内存流或缓存承载唯一可恢复数据。每块使用独立物理路径，完成后不可变；具体格式和块大小留待规格，不直接决定 CSV、JSON 或临时工作簿。
- 先关闭、校验并可靠发布数据块，再在 MySQL 短事务中核对有效执行权、预期前序断点和暂停控制，提交对该块的引用、下一段读取位置及相应进度。文件落盘与数据库提交不是同一事务；顺序不能反过来。
- 只有 MySQL 已提交清单引用的连续前缀才是可信断点。文件已写但登记结果不明时先回读，未提交的块只是残留；不能只凭文件存在或条数增加宣布保存成功。
- 接管者取得新执行权后校验该清单和数据块，从最后一个可信连续前缀之后读取并追加新块。旧尝试已提交的不可变块可以复用，新旧 Worker 不共同追加同一块。
- 不完整的末块允许丢弃并从上一可信断点重做。没有可用断点，或数据块确实损坏、丢失、无法兼容，且无法退回更早可信前缀时，才原子建立完整重建的新数据代次；原任务不变，旧代次块不混入新结果。
- 暂停任务即使没有执行租约，也必须保留其断点引用的数据块。不能按租约过期、没有活跃 Worker 或临时文件年龄自动清除可恢复数据。
- 临时文件在这里指任务执行期间的中间产物，不是进程退出后自动删除的文件。受控临时目录必须允许同主机接管者在 Worker 重启后读取；仍被断点引用的文件不得随进程退出、通道关闭或停机清理而删除。目录位置、可靠落盘及安全清理的具体机制留待规格和运行方案验证。

### 装配阶段：不要把半成品 Excel 当成检查点

- 数据块完整后，从已落盘临时数据块按清单顺序流式装配一个任务专属临时 Excel，不把完整导出数据或完整工作簿集中保存在进程内存中；装配结束、校验及结果提交仍遵守执行锁与隔离代次。
- 装配过程中暂停或异常时，保留已提交的数据块，不默认可以重新打开写了一半的 `.xlsx` 继续追加。恢复时若没有可信完整就绪文件，可从数据块重新装配 Excel，不重新读取已经保存的订单数据。
- 因此本提案提供的是数据阶段的持久断点续写，最终 Excel 装配可以重做；不是宣称 XLSX 的任何写入位置都能恢复。若要求装配阶段也必须续写，须另评审低层文件检查点和工作簿组装方案。
- 多出的中间存储、校验和装配成本须纳入现有性能与资源目标验证，不因方案提出而视为已经满足成功标准。

## 六、文件也必须隔离，不能只保护数据库

- 每次尝试写入独立的任务与代次命名空间。旧 Worker 和新 Worker 不共写同一工作簿，不使用会覆盖已有产物的固定物理文件名。
- 文件关闭、校验并安全发布为不可变产物后，当前执行者才能持有效执行权登记可核对的产物就绪证明；就绪证明不是 `SUCCEEDED`，不赋予下载资格。
- 任务成功与所选产物引用在同一 MySQL 事务中提交，并验证当前执行权。下载只解析 MySQL 已提交的成功产物引用；对用户的文件名不决定物理存储身份。
- 接管者首先核对业务终态和既有就绪证明：已成功就不重建；未终态但存在可信、完整、与任务配置一致且可访问的不可变产物时，可重新校验后以新代次提交该产物为结果，避免盲目再生成。
- 最终文件存在但缺少可信就绪证明时，视为未获认可的残留，不按文件名推断成功；先核对可信数据断点，再决定继续数据处理或重新装配，不能一律重读全部订单。文件已写好但尚未登记就绪时崩溃，允许留下孤儿，不允许错误宣布成功。
- 成功提交结果不明时先回读；已成功则保留所引用产物并结束，未确认时不得删除候选结果或把任务改成失败。
- 清理器只处理经 MySQL 裁决不再可采用、无有效尝试且未被断点或结果引用的残留；采用与清理之间须互斥。旧 Worker 不能只因自己失权就删除可能被接管者采用的数据块或就绪产物，更不能清理暂停断点、其他尝试或成功文件。

在本地文件方案下，接管者和下载实例必须能够访问相同的获批存储命名空间；本提案不自动引入对象存储或跨主机共享文件系统。多 Worker 可先限定在同主机、共同可访问的文件目录，若要求跨主机接管，须先评审相应存储与运行拓扑。文件不可访问时不能宣称已完成接管或成功下载。

## 七、多 Worker 竞态的裁决结果

| 竞态 | 候选裁决 |
| --- | --- |
| 多个 Worker 同时首次认领 | MySQL 只允许一个提交首次执行权；其他实例核对并等待，不生成文件 |
| 有效持有者续租与其他实例接管 | 数据库内串行裁决；成功且未过期的续租阻止接管，过期或已被替换的身份不能续租 |
| 多个实例同时接管过期任务 | 仅一个取得新代次并扣用恢复预算，失败者不计一次执行、不开始生成 |
| 用户暂停与异常接管同时发生 | 同一任务记录串行裁决暂停意图；暂停意图提交后不再发放运行权，已取得权利的实例只允许受控收尾 |
| 用户暂停与成功提交同时发生 | 先成功则任务已完成，不能伪装暂停；先暂停请求则禁止后续成功推进，先保存安全断点并停止 |
| 暂停尚未生效就收到恢复，或多次恢复并发 | 不提前启动第二执行者；只为已生效暂停生成一次有效恢复授权，旧控制版本不能覆盖新状态 |
| 数据块登记与接管或重建同时发生 | 旧执行身份和错误的前序断点被拒绝；只沿已提交连续清单推进，不把不同数据代次混成结果 |
| 旧实例迟到写进度、报错或提交成功 | 拒绝旧代次，不覆盖新尝试或业务终态 |
| 旧实例完成文件与新实例重建重叠 | 尝试级路径隔离，最多选中一个成功结果，未被采用的文件后续受控清理 |
| 成功提交与租约到期接管或耗尽失败 | 在同一任务裁决边界竞争；成功后不能接管或改失败，已接管后旧身份不能提交成功 |
| 成功事务提交后 ACK 丢失 | 重交付者核对终态并 ACK，不重复生成、不重复提交成功 |
| 文件就绪采用与残留清理并发 | MySQL 裁决采用资格或清理资格后再操作文件，不能仅凭一次无锁扫描删除 |

租约不能杀死停顿后恢复的旧进程，也不能撤回已发生的磁盘写入。因此数据库代次检查与文件命名空间隔离缺一不可；仅使用分布式锁或仅依赖 RabbitMQ 单次投递都不足以保护结果。

“同一个任务不能被两个 Worker 同时拿到有效锁”是本提案的保证；不是保证两个实例不会同时申请锁，也不是证明租约过期的旧进程物理上已经停止计算。若要求任何时刻都不允许两进程计算，需要先确认旧进程已终止再接管，会牺牲无法确认旧进程状态时的自动恢复能力，必须另行评审。

## 八、停机与资源故障

- 正常停机先停止接收新消息，在有界宽限内完成并核对当前任务，满足终态边界后才 ACK。
- 部署停机和用户暂停不是同一意图：停机保存安全断点后按异常恢复责任交接，不自动把任务改成等待用户恢复；已提交的用户暂停也不能因服务重启被忽略。
- 宽限到期先停止执行和续租，受控关闭相关通道。只有确认执行器停止并经数据库裁决后才可提前释放执行权；不能先释放再让旧线程继续写入。
- MySQL 不可用时暂停权威更新和结果提交，不以本地文件或缓存代替裁决。RabbitMQ 不可用时不提前 ACK，也不绕过 broker 另行调度 `RUNNING`；Redis 不可用不撤销 MySQL 执行权。
- 存储故障、磁盘不足和文件校验失败按获批失败分类处理；不在旧执行权失效后把错误覆盖到新尝试。健康告警与业务失败分开。

## 未选择的替代方案

| 方案 | 本期不选择的理由 |
| --- | --- |
| 收到消息或认领后立即 ACK | 改变现有确认边界，需要另建可靠执行调度与恢复责任，不在本提案中隐式引入 |
| 扫描所有 `RUNNING` 并创建恢复 Outbox | 与 broker 重交付形成双重调度；当前选择继续依赖原未确认命令 |
| 只用 Redis 锁或仅靠 `PENDING -> RUNNING` | 前者引入另一执行权事实源，后者无法隔离认领后的崩溃与迟到执行者 |
| 覆盖同一个正式文件 | 数据库拒绝旧执行者之后仍可能被其文件写入污染 |
| 把进度条或 SXSSF 私有临时文件直接当断点 | 条数不证明持久数据完整；选择独立不可变数据块和数据库断点清单，装配过程不假定可任意续写 |
| 每次异常都立即从头重建 | 不符合断点优先要求；只有可信断点无法继续时才回退完整重建 |
| 用户暂停后继续由 broker 自动接管运行 | 违背用户控制意图；暂停生效后等待显式恢复授权 |

## 评审事项与后续规格边界

待批准的核心取舍：MySQL 有期限执行锁与单调代次隔离；用户暂停生效后的消息确认和原任务显式恢复 Outbox；不可变数据块与数据库断点清单；异常有界自动接管、断点优先和无法继续才完整重建；最终 Excel 装配允许从已保存数据块重做；就绪产物对账与唯一结果引用；不可恢复或预算耗尽时自动失败；同主机共享可访问目录的本期边界。

用户暂停、恢复、重建后的进度展示和新增失败原因须同步产品需求与验收基线后才能实施。暂停生效 ACK 与恢复命令须显式同步已有 ADR，不能把过去只讨论创建命令的规则直接扩展。异常消息隔离和可靠 SSE 通知仍是独立架构待决项，不因本提案而获得批准。

后续规格再确定暂停状态、接口与控制版本，恢复命令与断点字段，数据块格式和大小，稳定读取游标、验证与兼容规则，事务隔离与 SQL、锁顺序、租约与心跳数值、尝试期限、恢复上限和退避、通道配置、broker 超时支持、进度事件、目录布局及清理参数。本 ADR 不提前固定这些细节。

未来需在真实 MySQL、RabbitMQ 和文件存储验证：认领提交未知、重复交付、用户暂停与接管或成功竞争、暂停收尾时崩溃、重复恢复、旧控制命令迟到、块发布与断点登记前后崩溃、续写前缀校验、完整重建隔离、连接存活但卡住、监督器停滞、续租与接管竞争、旧代次迟到、就绪登记前后崩溃、成功提交未知、ACK 丢失、恢复耗尽、暂停断点保留和文件采用与清理竞态。此清单是架构验证重点，不是已经生成或批准的测试任务。

本项目尚无生产实现。未来变更本方案时，先停止新增认领，核对有效租约、隔离代次、未确认命令和文件引用；不能通过重置代次、批量回退 `PENDING`、删除队列或清空工作目录回滚。

## 技术依据

- [RabbitMQ 发布与消费确认](https://www.rabbitmq.com/docs/confirms)：确认与业务执行不是同一机制，投递标识有通道作用域。
- [RabbitMQ 消费者](https://www.rabbitmq.com/docs/consumers)：预取、连接恢复与消费确认超时的官方说明；具体超时行为必须按本项目实际版本和队列类型验证。
- [MySQL 8.4 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)：并发读取后更新需使用事务裁决，具体 SQL 留待规格。
- [Apache POI SXSSF](https://poi.apache.org/components/spreadsheet/how-to.html#sxssf)：流式窗口、已刷出行的访问限制和工作簿写出说明，不把进程内窗口或私有临时文件直接等同于跨进程断点。

用户暂停交接、隔离代次、持久数据块断点、文件就绪对账和有界恢复是本项目的候选设计，不是上述资料已经为本项目保证的端到端语义。
