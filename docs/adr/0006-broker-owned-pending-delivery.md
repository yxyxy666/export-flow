# ADR-0006 已发送任务由 RabbitMQ 负责交付

- 状态：已接受（已发送命令的交付职责与消费确认边界）；认领/确认/恢复参数已按2026-10-07决策定稿，具体整体规格仍待审批
- 日期：2026-09-30
- 适用范围：原命令 Outbox 已确认发送后的 RabbitMQ 排队、交付和未确认消息恢复
- 依据：[产品需求](../product/order-export-prd.md)、[`AC-049`](../product/acceptance-criteria.md#ac-049)

## 背景

原命令 Outbox 已标记 `SENT` 后，任务仍为 `PENDING`，并不能证明消息丢失：它可能安全地排在 RabbitMQ 中，也可能已交付但尚未被 Worker 认领。按固定时间自动补投会放大队列积压；随后把正常排队的任务判为失败会误伤用户。因此 MySQL 不承担 RabbitMQ 的交付与重投职责。

## 决策

1. 创建任务及待发送命令仍在同一 MySQL 事务提交。Outbox dispatcher 在 RabbitMQ 发布确认且正确路由后标记 `SENT`；未确认发送时在 [`ADR-0007`](0007-outbox-dispatch-retry.md) 的总窗口内重试，到期未开工则自动失败并关闭原命令。该规则不适用于已 `SENT` 的正常排队任务。
2. `SENT` 之后不因任务保持 `PENDING` 达到固定时长而自动创建恢复 Outbox，也不因排队时长自动把任务改为 `FAILED`。消息交付、未确认消息重新入队由 RabbitMQ 及其消费者协议负责；队列必须采用可恢复的持久化拓扑，发布确认、正确路由检查、手动消费确认和断连重投须在整体 RabbitMQ 方案中验证。
3. RabbitMQ 交付消息时会记录该投递尚未被消费确认；这不等于 MySQL 任务进入 `RUNNING`。Worker 收到消息后应立即尝试 MySQL 条件认领，首次仅在 `PENDING -> RUNNING` 提交成功后生成；异常恢复仅按[ADR-0008](0008-worker-execution-lease-and-recovery.md)到期授权取得新执行权，不能凭重交付直接生成。消费者预取量须结合并发与长任务容量确定，不在此固定。认领前异常或断连时不能提前确认消息；RabbitMQ 连接/通道关闭后重新交付未确认消息。
4. 沿用现阶段“业务终态提交，或 MySQL 权威状态证明该消息无需处理后，才手动确认消费”的边界。**不能仅因 Worker 收到消息就确认消费**，否则收到后崩溃会让消息从队列消失。认领前连接仍存活却卡住时，RabbitMQ 只知道消息未确认，不知道 Worker 是否已提交 MySQL `RUNNING`。应用侧消费监测器须按交付时间和 MySQL 状态识别认领停滞，告警并在有界时间后关闭对应消费通道；通道关闭后，RabbitMQ 才重新入队并交付未确认消息。监测器、通道隔离、认领阈值和误判防护须在实现规格中验证。
5. RabbitMQ 的消费确认超时是未确认投递的兜底保护，不能直接拿短的“认领超时”值配置它：当前 ACK 留到长时间文件生成结束，两种时钟覆盖不同阶段。消费端可在认领前关闭卡住的通道；认领成功后须由另行批准的[执行恢复方案](0008-worker-execution-lease-and-recovery.md)处理，不能因 ACK 暂未到来就盲目重做文件。已确认发送但长期 `PENDING` 的任务、队列积压、未确认消息数与消费者健康须可监控和告警；一般积压告警不自动复制消息或改写业务终态。极端的已确认消息丢失或队列被误删，须在核对 MySQL 与 RabbitMQ 后受控修复，不靠固定时间猜测。

## 理由与后果

MySQL 仍裁决任务是否创建、是否开工及最终结果；RabbitMQ 负责已接收消息的排队、交付和断连重交付。无需在 MySQL 中伪造“已分配给哪个 Worker”的业务状态。该选择减少重复消息和误判失败，但 Worker 或队列长期不可用时，任务可能持续 `PENDING`；监控告警和运维修复不可省略。消息消费确认留到终态意味着长任务会占用未确认投递，确认超时必须与最长允许执行时间协调；若将来改为认领后确认，必须先批准可靠的 MySQL 租约与执行恢复机制，另立决策。

## 评审与回退

在真实 MySQL/RabbitMQ 上验证：安全排队超过告警阈值仍不补投、不误判失败；Worker 认领前断连导致重交付；收到消息但未认领时不确认；终态后确认；重复投递只允许一次执行；消费者连接存活却卡住时由应用侧监测器关闭对应通道并重交付；长任务执行期间不因认领超时被误关。项目尚无生产实现；实施后若改变交接边界，先核对活跃任务、Outbox、未确认消息和租约，再更新状态与消费确认契约。
