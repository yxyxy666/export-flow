# 测试与验收追踪规则

## 基本原则

- 进入实施阶段后，行为变更先写失败测试或记录经批准的覆盖缺口，再写生产实现；缺陷先写可复现的回归测试。讨论需求和学习流程时不因此生成规格或测试。
- 测试名称描述条件和可观察结果，不描述私有实现；数据最小、可读、可重复。时间、随机 ID、并发屏障、网络和文件目录应可控制，不用固定等待掩盖竞态。
- 领域行为优先用单元测试，模块协作用组件或切片测试，真实数据库、消息、缓存、文件和协议边界用集成及契约测试；性能目标单独验证。
- 覆盖率是信号，不替代业务断言。新增成功、拒绝、失败和边界分支须有可判定结果；不得用放宽断言、无条件重试或增加固定等待处理不稳定测试。

## AC/SC 唯一来源与映射

[`acceptance-criteria.md`](../product/acceptance-criteria.md) 是所有验收与成功标准编号、定义的唯一来源。其他文档提到具体编号时须链接到其锚点，不复制定义或裸写编号；编号不得复用，含义变化须建立新编号。

- 功能进入规格阶段时，`tasks.md` 分别维护 AC 到实现任务、AC 到测试用例、SC 到验证用例的映射。产品讨论期尚未建立规格，不视为映射缺陷。
- 每条进入实施范围的 AC 至少对应一个实现任务和一个测试用例；不能自动化时记录理由、替代验证、责任人和评审结论。每条 SC 对应验证用例、运行环境和证据位置，不能仅写“测试通过”。
- 任务编号 `T-xxx` 在单个功能规格内唯一；测试编号 `TC-xxx` 全项目唯一。测试名称、注释或元数据引用对应 AC，跨功能复用同一测试时不得重新分配其编号。
- 实施前与提交前检查缺少实现映射、测试映射、SC 环境或证据的标准；检查只覆盖复合标准部分断言、误标“不适用”和悬空链接的用例。

## 工具与真实边界

- 前端测试栈由 [`ADR-0002`](../adr/0002-frontend-stack-and-test-scope.md) 确定：Vitest、Testing Library 和 MSW。单元、组件、功能集成与契约测试各验证相应边界；本期不设置浏览器端到端测试门禁。
- 后端测试工具基线仍待审批，候选为 JUnit Jupiter、AssertJ、Spring Boot Test、MockMvc 与 Testcontainers；候选不能当作已获批初始化要求。
- 事务、锁、迁移、唯一约束和查询语义必须用隔离的真实 MySQL 验证。RabbitMQ 的发布/消费与 Redis 的缓存恢复须在对应真实依赖上验证；不得用 H2、mock repository、内存队列或内存缓存代替关键一致性测试。
- 测试环境不依赖线上服务、真实密钥、共享数据库或前一用例残留。schema、队列和缓存数据须隔离；时间、ID 和并发次序可注入或由屏障控制。
- API 与消息契约测试验证版本、错误结构、未知枚举、缺失字段和兼容策略。文件测试使用临时目录，验证关闭、可读性、安全发布、失败清理与下载边界。

## 性能、证据与质量门禁

- 性能和资源 SC 使用独立配置、固定数据、预热、重复测量及环境记录；不能把普通 CI 的偶发运行时间当作产品性能证据。参考环境未获批准前，相应 SC 不能判定通过。
- 测试数据、日志、截图和报告只使用合成信息，保留经脱敏的失败证据。接口时间断言指定 UTC，人类展示断言指定产品时区，不依赖机器默认时区。
- 跳过、隔离和预期失败测试须记录原因、责任人和恢复条件；关键 AC/SC 不得长期跳过。具体 CI、构建及打包门禁尚未制定，见 [`build.md`](build.md)。

订单导出的具体测试场景待进入实施阶段后，由获批规格形成正式映射和用例。
