# 测试与验收追踪规则

## 基本原则

- 进入实施阶段后，行为变更先写失败测试或记录经批准的覆盖缺口，再写生产实现；缺陷先写可复现的回归测试。讨论需求和学习流程时不因此生成规格或测试。
- 测试名称描述条件和可观察结果，不描述私有实现；数据最小、可读、可重复。时间、随机 ID、并发屏障、网络和文件目录应可控制，不用固定等待掩盖竞态。
- 领域行为优先用单元测试，模块协作用组件或切片测试，真实数据库、消息、缓存、文件和协议边界用集成及契约测试；性能目标单独验证。
- 覆盖率是信号，不替代业务断言。新增成功、拒绝、失败和边界分支须有可判定结果；不得用放宽断言、无条件重试或增加固定等待处理不稳定测试。

## 测试先行阶段与审批

需要规格的功能先由项目负责人明确批准 `spec.md`、`plan.md`、`tasks.md` 及相关附属产物，
才能开始测试先行阶段；该审批不授权生产代码实施。规格内容遵循[规格准备规则](specification.md)。

测试先行阶段允许按获批计划创建测试文件、测试专用夹具和替身、运行器及执行测试必需的依赖配置。
项目尚未初始化时，计划须区分测试工具准备和正式工程实现；不得借准备测试提前编写生产入口、
业务实现、生产迁移、正式基础设施适配器或生产目录中的空壳代码。必要替身只放在测试范围，
且不得冒充真实数据库、消息或其他关键边界的集成证据。

测试阶段门禁通过须满足（项目负责人已于 2026-10-04 确认该口径）：

1. 测试环境正常，运行器、测试依赖及计划要求的隔离服务已就绪；环境故障须先解决，不能以故障状态宣称门禁通过。
2. 约定审批范围内的测试用例已编写，验收映射完整，成功、拒绝、失败及关键边界均有明确断言；已运行可执行测试，保留命令、环境和实际结果，新增行为的预期失败明确指向尚未实现的目标行为。
3. 因工程或接口尚不存在而无法执行的测试、不能自动化的行为及其他覆盖缺口，单独说明原因、影响、替代验证和恢复条件，提交项目负责人评审。导入、编译、工具或连接故障不能冒充行为红灯。
4. `tasks.md` 的测试进度与证据完整，提交测试先行阶段审批；只有项目负责人明确批准本阶段及其中的覆盖缺口，才可在批准范围内编写生产代码。

“测试通过后正式开发”指上述测试阶段门禁通过并获项目负责人明确审批，不表示尚未实现的业务测试全部通过；
已存在行为的回归测试可能保持绿灯，新增行为须有红灯或经批准的覆盖缺口。
模型自检、测试自动通过和规格审批均不能代替对测试先行阶段及实施范围的明确批准。

## 进度与证据记录

每次准备规格时，在 `tasks.md` 初始化测试进度表，尚未开始的项目记录为“未编写／未执行”，
不能把测试设计完成记作测试代码已完成。阶段状态依次记录“未开始、准备中、待审批、已批准”；
测试执行状态、门禁检查结果与审批状态分别维护，不使用含糊的“测试完成”替代实际结果。

| 记录项 | 必填内容 |
| --- | --- |
| 测试范围 | 测试任务和用例编号、相关验收或成功标准链接、目标文件 |
| 编写与执行进度 | 未编写／编写中／已编写；未执行／已执行／阻塞；执行日期 |
| 实际结果 | 预期行为失败／通过／环境或编译阻塞／覆盖缺口，及原因 |
| 可复现证据 | 命令、运行环境、报告或日志位置；尚未执行时记录计划位置并明确不存在实际证据 |
| 覆盖缺口 | 影响、替代验证、负责人、恢复条件、项目负责人审批结论 |
| 审批 | 规格与测试先行阶段分别记录批准人、日期、范围、版本或提交标识、结论依据 |
| 门禁检查 | 测试环境、用例完整性、预期失败证据和覆盖缺口评审的逐项结果，与审批结论分开记录 |

实现后的绿灯、回归和 SC 度量继续更新同一进度表，不覆盖或删除测试先行阶段证据。
新增行为或范围变更重新准备受影响测试并取得对应审批，不能沿用无关范围的旧批准。

## AC/SC 唯一来源与映射

[`acceptance-criteria.md`](../product/acceptance-criteria.md) 是所有验收与成功标准编号、定义的唯一来源。其他文档提到具体编号时须链接到其锚点，不复制定义或裸写编号；编号不得复用，含义变化须建立新编号。

- 功能进入规格阶段时，`tasks.md` 分别维护 AC 到实现任务、AC 到测试用例、SC 到验证用例的映射。产品讨论期尚未建立规格，不视为映射缺陷。
- 每条进入实施范围的 AC 至少对应一个实现任务和一个测试用例；不能自动化时记录理由、替代验证、责任人和评审结论。每条 SC 对应验证用例、运行环境和证据位置，不能仅写“测试通过”。
- 任务编号 `T-xxx` 在单个功能规格内唯一；测试编号 `TC-xxx` 全项目唯一。测试名称、注释或元数据引用对应 AC，跨功能复用同一测试时不得重新分配其编号。
- 实施前与提交前检查缺少实现映射、测试映射、SC 环境或证据的标准；检查只覆盖复合标准部分断言、误标“不适用”和悬空链接的用例。

## 工具与真实边界

- 前端测试栈由 [`ADR-0002`](../adr/0002-frontend-stack-and-test-scope.md) 确定：Vitest、Testing Library 和 MSW。单元、组件、功能集成与契约测试各验证相应边界；本期不设置浏览器端到端测试门禁。
- 后端测试基线已由[ADR-0009](../adr/0009-engineering-runtime-and-progress-notification.md)确定为JUnit Jupiter、AssertJ、Spring Boot Test、MockMvc与Testcontainers；精确版本见[版本表](../../specs/002-order-management/dependency-versions.md)。选型确认不构成规格或测试代码生成授权。
- 事务、锁、迁移、唯一约束和查询语义必须用隔离的真实 MySQL 验证。RabbitMQ 的发布/消费与 Redis 的缓存恢复须在对应真实依赖上验证；不得用 H2、mock repository、内存队列或内存缓存代替关键一致性测试。
- 测试环境不依赖线上服务、真实密钥、共享数据库或前一用例残留。schema、队列和缓存数据须隔离；时间、ID 和并发次序可注入或由屏障控制。
- API 与消息契约测试验证版本、错误结构、未知枚举、缺失字段和兼容策略。文件测试使用临时目录，验证关闭、可读性、安全发布、失败清理与下载边界。

## 性能、证据与质量门禁

- 性能和资源 SC 使用独立配置、固定数据、预热、重复测量及环境记录；不能把普通 CI 的偶发运行时间当作产品性能证据。参考环境未获批准前，相应 SC 不能判定通过。
- 测试数据、日志、截图和报告只使用合成信息，保留经脱敏的失败证据。接口时间断言指定 UTC，人类展示断言指定产品时区，不依赖机器默认时区。
- 跳过、隔离和预期失败测试须记录原因、责任人和恢复条件；关键 AC/SC 不得长期跳过。本期本地门禁与产物保存已经确定，远程CI和发布明确延期，见 [`build.md`](build.md)。

订单导出的测试场景与追踪映射在规格阶段设计；规格获批后才编写和执行测试代码，
测试阶段门禁通过并经项目负责人明确批准后才进入生产实现。
