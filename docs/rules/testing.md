# 测试与验收追踪规则

## 1. 基本原则

- 行为变更先写失败测试或记录经批准的覆盖缺口，再写实现；缺陷先写可复现的回归测试。
- 测试按金字塔组织：领域单元测试优先，模块协作用组件/切片测试，真实边界用集成和契约测试，性能目标用独立性能验证。
- 测试名称描述条件和可观察结果，不描述私有实现；数据最小、可读、可重复。
- 时间、随机 ID、并发屏障、网络和文件目录必须可控制；禁止用固定等待掩盖竞态。
- 外部依赖通过 fake、mock 或测试容器隔离；不得依赖线上服务、真实密钥、共享数据库或前一用例残留。
- 覆盖率是信号而非验收替代物。新增成功、拒绝、失败和边界分支都必须有断言。

## 2. AC/SC 唯一来源与链接

[`acceptance-criteria.md`](../product/acceptance-criteria.md) 是所有 `AC` 和 `SC` 编号及定义的唯一来源。

- 产品、规则、规格、计划、任务、测试报告和 ADR 提到具体编号时，必须使用可点击链接直达该编号锚点，不得只写裸文本。
- 其他文档不得复制或改写 AC/SC 定义；需要解释时链接原定义并描述本文件负责的实现或验证部分。
- AC 和 SC 编号全项目唯一且不可复用。行为或度量含义实质变化时新增编号，旧编号标记为“已取代”。
- `AC-xxx`、`SC-xxx` 仅用于讲解编号格式，不代表具体标准，可以不链接。
- 功能规格的 `tasks.md` 必须分别维护“AC—实现任务”“AC—测试用例”和“SC—验证用例”映射。
- 每个测试名称或元数据必须包含对应编号，例如测试名可写为 `TC-031` 并关联 [`AC-006`](../product/acceptance-criteria.md#ac-006)；测试代码因格式限制不能使用 Markdown 链接时，测试旁的映射表必须提供链接。

例如：[`AC-006`](../product/acceptance-criteria.md#ac-006) 可映射多个实现任务和测试，[`SC-003`](../product/acceptance-criteria.md#sc-003) 可映射功能、性能和文件可读性验证。不得根据编号接近推断映射关系。

## 3. 追踪完整性

- 每条 AC 至少映射一个直接实现任务和一个测试用例；无法自动化时记录原因、替代验证、责任人和评审结论。
- 每条 SC 至少映射一个验证用例、运行环境和证据位置。SC 可以由自动化性能测试、资源约束测试、视觉检查或质量门禁验证，但不得仅写“人工确认”。
- 实现任务使用 `T-xxx`，编号在各 `specs/<feature-dir>/` 内唯一，跨规格引用时必须同时给出功能目录；测试用例使用全项目唯一的 `TC-xxx`，跨规格共同覆盖时复用同一个用例及含义，不得把同一编号分配给不同测试。性能或运行手册验证仍使用 `TC-xxx`，通过层级字段区分。
- 一个用例覆盖多条标准时，必须逐项列出并保留独立断言。
- 准备、基础设施和纯文档任务可以标记“AC/SC：不适用”，但必须说明原因。

测试先行和提交前必须检查：

1. 未映射实现任务的 AC。
2. 未映射测试用例的 AC。
3. 未映射验证用例、环境或证据的 SC。
4. 直接实现或验证行为但未声明编号的任务/用例。
5. 只覆盖复合标准部分断言的用例。
6. 错误标记“不适用”或没有说明理由的任务。
7. 指向不存在锚点、错误文件或裸写的具体 AC/SC 引用。

## 4. 前端测试

前端同时遵守 [`frontend.md`](frontend.md)。测试栈为 Vitest + Testing Library + MSW；本期不设置浏览器端到端测试门禁。

### 4.1 分层

- 领域单元测试：范围校验、query 解析、枚举兜底、进度计算、动作权限、格式化和 DTO 映射，不启动浏览器或真实网络。
- 组件测试：筛选、表格、对话框、跨页选择、导出字段、禁用原因以及 `loading/empty/error/success`，通过角色、可访问名称和可见文本定位。
- 前端集成测试：路由、功能状态和 API client 协作，包括请求取消、旧响应隔离、缓存失效、幂等键、SSE 生命周期和下载失败。
- 契约测试：请求/响应、错误体、分页、枚举、任务状态、SSE 事件和下载响应头；协议变化必须在 CI 暴露不兼容。

### 4.2 必测行为

- 路由覆盖合法 query 恢复、非法 query 规范化、前进/后退和编辑值不污染已提交查询。
- 跨页选择证明切页保留、未提交修改不清空、提交新查询或重置后清空。
- 异步请求覆盖乱序、取消、卸载、重复提交、超时和安全重试。
- 幂等测试区分同一次提交的传输重试和用户新建/重试任务。
- 下载覆盖允许/禁用状态、直接下载 URL、错误和安全文件名。本期不验证真实浏览器保存文件，缺口通过后端文件集成测试补足。
- 可访问性覆盖键盘、焦点进入/返回、标签、错误关联、禁用原因和状态非纯颜色表达。
- 响应式至少验证 1280×720 和典型桌面视口，业务断言不能只依赖截图。

### 4.3 SSE 测试

- 项目只使用 SSE，不注册固定或低频轮询。测试必须断言可控时间推进不会产生周期性列表请求。
- 初次进入、恢复可见、恢复联网和手动刷新允许一次快照查询；发现活跃任务后只建立一个 EventSource。
- 本客户端创建/重试成功及同浏览器跨标签页通知必须唤醒唯一连接。
- 进度事件覆盖去重、乱序、旧连接世代、终态不回退和无效计数。
- 有效 `stream-idle` 使前端调用 `close()` 且不自动重连；无标记异常断线走有界退避和回补。
- 本地有创建/重试请求未完成时到达空闲标记，必须覆盖新活动优先的竞态。
- 页面隐藏或离开、组件卸载和浏览器离线必须释放连接与监听器；恢复行为按已批准生命周期验证。

## 5. 后端测试

### 5.1 建议工具基线（待审批）

- JUnit Jupiter、AssertJ、Spring Boot Test。
- MockMvc 用于 MVC API 切片；若最终选择 WebFlux，则改为 WebTestClient，二者不并存。
- Testcontainers MySQL 8.4 LTS、RabbitMQ 与 Redis 8 用于 repository、迁移、事务、幂等、outbox、RabbitMQ 任务队列和拟议 Redis 进度缓存的隔离集成测试；缓存方案和 SSE 通知机制须待 [`ADR-0006`](../adr/0006-backend-stack-and-progress-cache.md) 批准后落成测试契约。禁止使用 H2、内存队列或内存 Redis 替代真实边界。
- Apache POI 读取生成文件以验证 workbook、sheet、表头、列顺序、类型、时区和行数。

测试框架和插件版本由 Maven dependency management 与 Wrapper 固定。工具基线获批前不得据此初始化项目。

### 5.2 分层

- 领域单元测试：状态机、范围、字段、进度、错误分类和幂等请求摘要，不加载 Spring context。
- Application 测试：用 fake ports 验证事务外编排、失败处理、重试创建新任务和状态不变量。
- API 切片测试：校验 DTO、HTTP 状态、错误体、分页、下载头和 SSE 事件序列，不 mock 领域规则本身。
- MySQL/RabbitMQ/Redis 集成测试：迁移、InnoDB 事务、字符集与排序规则、查询边界、稳定排序、唯一幂等键、outbox、RabbitMQ 发布/消费、条件状态更新和恢复；Redis 缓存与 SSE 广播按获批契约补足。
- 文件集成测试：临时目录中生成、关闭、校验、原子发布、下载和失败清理，不写开发者固定目录。
- 契约测试：OpenAPI 与控制器行为、前后端夹具和 SSE 事件 schema 一致。

### 5.3 数据库与并发

- 每个用例在隔离 schema/容器或可证明的事务清理后运行，不依赖执行顺序。
- 迁移同时验证空库升级和上一受支持版本升级；失败迁移不得留下伪成功状态。
- MySQL 集成测试必须验证 InnoDB、`utf8mb4`、明确的大小写敏感排序规则、UTC 会话时区、严格 SQL 模式及获批隔离级别；不得依赖测试容器镜像的隐式默认值。
- outbox 并发领取和任务条件更新必须在真实 MySQL 上验证锁等待、冲突、提交与回滚结果；测试不能用 H2 或 mock 推断 MySQL 锁语义。
- 时间、ID 和调度器可注入；并发测试使用 latch/barrier 协调，不使用 `sleep` 猜测时序。
- 至少验证两个 consumer 竞争同一任务消息时只有一个通过 MySQL 条件更新开始处理，重复消息不会生成第二个文件。
- 创建幂等至少验证同键同载荷、并发同键、同键不同载荷，以及事务回滚后能否安全重试。
- 状态/进度更新验证终态不回退、进度不减少、处理数不越界和迟到更新被拒绝。
- 任务创建事务回滚时不得留下命令 outbox；事务成功但 RabbitMQ 不可用时命令 outbox 保留，恢复后可幂等投递。进度先提交 MySQL；Redis 缓存不可用不得回滚已提交进度，恢复后可从 MySQL 重建。进度 outbox 是否保留及其发布目标待 ADR 评审。
- 命令 dispatcher 覆盖“发布 RabbitMQ 前”“发布确认后、标记 outbox 前”和“标记后”的崩溃点；进度通知的崩溃窗口须待跨实例广播方案批准后定义，不沿用 Redis Stream 的写入测试。
- RabbitMQ consumer 崩溃点覆盖“领取后、声明前”“声明后、生成中”和“终态提交后、手动确认前”，验证重新投递、MySQL 租约和重复消费。
- RabbitMQ 重启、消息无法路由或队列不可用，以及 Redis 缓存重启、过期和版本落后，均需有可判定结果；不得通过清空基础设施规避恢复测试。
- worker 崩溃恢复的租约、最大尝试次数和死信参数等待审批，参数确认前测试场景必须保留为覆盖缺口。

### 5.4 RabbitMQ 命令与 Redis 进度缓存契约

- RabbitMQ 任务命令使用版本化 schema，至少包含事件 ID、类型、版本、任务 ID、发生时间和必要追踪字段；进度通知的事件 schema 待跨实例方案审批。
- 消息不得包含客户姓名、手机号、完整筛选条件、文件物理路径、幂等键或其他不必要敏感数据。
- 测试消息版本兼容、缺字段、未知类型、重复 ID、乱序和畸形载荷；不可处理的 RabbitMQ 命令进入有界诊断/死信流程，不能阻塞后续任务。
- RabbitMQ exchange、queue、routing key 及 Redis 进度缓存 key 必须按环境/应用隔离；测试间使用独立拓扑和缓存前缀。
- RabbitMQ 发布确认且正确路由后才能标记命令 outbox 已发布；业务终态持久化或权威状态证明无需处理后才能手动确认消费。

### 5.5 Excel 与文件

- 小数据精确验证行、列、表头、字段选择、顺序、金额、枚举和 `Asia/Hong_Kong` 秒级时间。
- 边界数据覆盖空结果、1 行、跨批次边界、110,000 行和 200,000 行；大数据测试放入独立性能配置，不拖慢普通单元测试。
- 生成成功必须先关闭并可由 POI 重新打开，再发布文件和提交成功状态。
- 注入查询、写入、关闭、移动和数据库更新失败，验证任务失败、资源关闭、临时文件清理及成功文件不被误删。
- 下载验证状态、内容类型、长度（可得时）、安全 `Content-Disposition`、不存在文件和路径穿越。

### 5.6 后端 SSE

- 使用可控时钟和活动版本测试空闲宽限期，不使用真实等待。
- 创建/重试提交与空闲复核通过并发屏障覆盖三种顺序：新任务先提交、空闲先确认、无法证明严格先后；后者必须新活动优先。
- `stream-idle` 仅在活跃集合为空且活动版本未变化时发送，发送后响应正常结束。
- 异常关闭不得伪造 `stream-idle`；连接取消、超时和服务关闭释放 emitter 与订阅资源。
- 验证 MySQL 状态/进度不回退；Redis 缓存缺失、过期或版本落后时从 MySQL 获取权威快照，断线时不能假设缓存包含事件历史。事件 ID 与回补协议待审批后补完整断言。
- 多后端实例必须分别收到所需进度通知并只向本地 SSE 连接广播；通知机制、在线漏通知补偿和失败注入测试待 [`ADR-0006`](../adr/0006-backend-stack-and-progress-cache.md) 审批后明确，不能用工作队列竞争消费来模拟广播。
- 断言任务进度没有任何轮询依赖。

## 6. SC 与性能验证

- 性能 SC 不进入普通功能测试的硬编码超时；使用独立 Maven profile、固定数据、预热、重复次数和报告。
- P95、导出耗时和 512 MB 堆约束必须记录 CPU、内存、磁盘、容器资源、JVM 参数、数据库配置和样本数。
- CI 资源不稳定时，功能 CI 只验证性能测试可运行；正式 SC 证据在批准的本地参考环境产生并归档。
- 文件可打开、行数、列顺序和幂等结果必须自动化，不得因属于 SC 而降为纯人工检查。
- 参考环境尚未定义，因此 [`SC-001`](../product/acceptance-criteria.md#sc-001) 至 [`SC-004`](../product/acceptance-criteria.md#sc-004) 当前不能判定通过。

## 7. 隔离、数据与证据

- 只使用合成姓名、手机号、订单和文件；日志、截图、报告和 trace 同样不得包含真实信息。
- 接口断言使用 UTC，页面、Excel 和文件名断言显式使用 `Asia/Hong_Kong`，不得依赖机器默认时区。
- API fake/mock 从已确认契约集中生成或维护，未知枚举和缺失字段使用专用夹具。
- 测试失败保留经脱敏的请求摘要、日志、报告或截图；成功制品按构建规则归档。
- 不允许无条件重试、增加固定等待或削弱断言处理不稳定测试。重试只用于诊断，必须记录责任人和修复期限。

## 8. 质量门禁

- 前端：格式化、静态分析、类型检查、单元、组件/集成、契约测试和生产构建。
- 后端：格式化、静态分析、单元、MySQL/RabbitMQ/Redis 集成、契约测试、打包和产物检查。
- 新增分支必须有断言；覆盖率阈值待初始基线形成后审批，不得临时降低。
- 跳过、隔离或预期失败测试必须关联原因、责任人和恢复条件；关键 AC/SC 不得长期跳过。
- CI 和本地命令与 [`build.md`](build.md) 一致，并在项目初始化后记录到 README。
