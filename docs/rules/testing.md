# 测试规则

- 测试按金字塔组织：纯业务单元测试优先，组件交互和模块协作用组件/集成测试覆盖，前后端边界用契约测试覆盖。
- 测试名称描述行为和条件，不描述实现细节；测试数据使用最小、可读、可重复的夹具。
- 每个缺陷先增加能复现问题的失败测试，再修改实现；修复后保留该回归测试。
- 外部服务通过稳定的 fake/mock 或测试容器隔离；不得依赖线上服务、真实密钥或不可控时间。
- 覆盖率是信号而非唯一门槛；新增分支必须有对应成功、失败和边界断言。

## 前端测试规则

前端测试同时遵守 [`frontend.md`](frontend.md) 的架构、状态、接口、可访问性和隐私约束。根据 [`ADR-0002`](../adr/0002-frontend-stack-and-test-scope.md)，前端采用 Vitest + Testing Library + MSW；具体版本和命令在项目初始化时锁定。

本期为本地学习项目，不引入端到端测试、生产监控、认证/授权或合规测试。关键验收行为必须由单元、组件、前端集成或契约测试覆盖；确实无法在这些层级自动化时，按本文既有覆盖缺口规则记录替代验证方式和评审结论。

### 测试分层

- 领域单元测试覆盖纯函数和业务不变量，包括时间/金额范围校验、路由 query 解析、枚举兜底、进度计算、动作权限、格式化和 DTO 映射。此层不得启动浏览器或真实网络。
- 组件测试从用户可观察行为出发，覆盖表单、表格、对话框、跨页选择、导出字段、禁用原因及 `loading`、`empty`、`error`、`success`。通过语义角色、可访问名称和可见文本定位元素，不依赖 CSS 类名或组件内部状态。
- 前端集成测试覆盖路由、功能状态与 API client 的协作，包括 query 序列化、请求取消、旧响应隔离、缓存失效、轮询生命周期、幂等键和下载失败。网络应在传输边界模拟，不 mock 被测功能自身的领域规则。
- 契约测试验证前后端共享的请求、响应、错误体、分页、枚举、任务状态及下载响应头。契约变更必须能够在 CI 中暴露破坏性不兼容。

### 用例设计

- 测试名称或元数据必须按本文后续规则引用对应 `AC-xxx`，例如 `TC-031 [AC-006] 创建已选订单导出任务`；一个用例覆盖多个 AC 时逐项列出并分别断言。
- 同时覆盖用户成功路径、业务拒绝、协议异常、网络失败、空数据和边界值，不得只验证组件“能够渲染”。
- 路由测试必须覆盖合法 query 的恢复、非法 query 的规范化、浏览器前进/后退，以及编辑中筛选值不提前污染已提交 query。
- 跨页选择测试必须证明切页保留选择、修改条件但未查询时不清空、修改条件并查询后清空，以及重置清空。
- 异步测试必须覆盖请求乱序、取消、组件卸载、重复提交、超时和重试，不得使用固定等待时间掩盖竞态。
- 轮询测试使用可控时间，验证任务页可见时每 3 秒刷新（包括当前页无活跃任务）、请求不重叠、离开或切后台时暂停、恢复可见立即刷新、失败后下个周期重试，以及旧进度不覆盖新状态。
- 幂等测试必须区分“同一次提交的传输重试”和“用户发起的新任务”：前者复用 `Idempotency-Key`，后者生成新键。
- 下载测试至少验证允许状态、禁用状态、直接下载 URL、服务端业务/网络错误及 `Content-Disposition` 文件名处理。本期不验证真实浏览器下载，也不测试登录和权限流程；相关缺口必须记录替代验证方式。
- 可访问性测试覆盖键盘操作、焦点进入/返回、标签和错误关联、禁用原因、状态非纯颜色表达。自动扫描不能替代关键流程的键盘和读屏语义人工检查。
- 响应式测试至少覆盖确认后的最小视口和典型桌面视口，验证主要操作可达、文本不遮挡、表格可理解；关键页面可采用稳定的视觉回归，但不得只用截图快照判断业务正确性。

### 隔离、数据与稳定性

- 测试使用合成的姓名、手机号、订单和文件，不复制生产数据、真实令牌或可识别个人信息。测试输出、截图、录像和错误日志同样遵守隐私规则。
- 时间、时区、随机 ID 和网络响应必须可控制；断言业务时间时固定时钟，接口断言使用 UTC，页面、Excel 和文件名断言显式使用 `Asia/Hong_Kong`，不得依赖执行机器本地设置。
- API fake/mock 必须来自已确认契约并集中维护。不得在各测试中散落互相矛盾的响应结构；未知枚举和缺失字段应有专门夹具。
- 集成测试环境使用隔离且可重复初始化的数据。用例不得依赖执行顺序、线上服务、前一用例残留或共享用户的可变状态。
- 测试失败时保留足以定位问题且经过脱敏的请求摘要、截图、录像或 trace。成功运行不默认长期保留含业务数据的制品。
- 不允许通过无条件重试、增加固定等待或降低断言来处理不稳定测试。重试只能用于收集诊断证据；确认不稳定后必须记录责任人和修复期限。

### 前端质量门禁

- 提交前至少通过格式化、静态分析、类型检查、领域单元测试、组件/集成测试和生产构建；本期不设置端到端测试门禁。
- 新增或修改的业务分支必须有相应断言。全局覆盖率及变更行覆盖率阈值在测试栈和初始基线确认后写入规则，不得临时降低门槛使变更通过。
- 任何跳过、隔离或预期失败的测试都必须关联问题记录、原因和恢复条件；不得把关键 AC 对应测试长期标记为跳过。
- 前端测试命令和 CI 阶段必须与 [`build.md`](build.md) 保持一致，并在项目初始化后记录在 README。

## 验收标准与测试追踪

- 验收标准（Acceptance Criteria）使用稳定且唯一的 `AC-xxx` 编号。
- 每条 AC 必须是原子、可观察、可判定的行为断言，至少能明确前置条件、触发动作和预期结果；“系统支持某功能”这类无法直接断言的表述不得作为合格 AC。
- 实现任务使用独立的 `T-xxx` 编号，测试用例使用独立的 `TC-xxx` 编号。不得根据编号相同或数字相近推断它们之间存在映射关系。
- AC 与实现任务、AC 与测试用例之间分别允许一对多、多对一和多对多关系：一个 AC 可以拆分到多个实现任务或测试用例，一个实现任务或测试用例也可以覆盖多个 AC；必须通过两张独立的显式映射表记录关系，不得用同一行暗示实现任务与测试用例直接配对。
- AC 与实现任务的映射表至少包含 `AC ID`、`实现任务 ID`、`实现覆盖说明`：

  | AC ID | 实现任务 ID | 实现覆盖说明 |
  |---|---|---|
  | AC-006 | T-021 | 创建异步导出任务 |
  | AC-006 | T-022 | 保存导出字段 |
  | AC-008 | T-021 | 支持按筛选结果创建任务 |

- AC 与测试用例的映射表至少包含 `AC ID`、`测试用例 ID`、`测试层级`、`验证说明`：

  | AC ID | 测试用例 ID | 测试层级 | 验证说明 |
  |---|---|---|---|
  | AC-006 | TC-031 | integration | 验证异步导出任务创建成功 |
  | AC-006 | TC-032 | integration | 验证所选导出字段被正确保存 |
  | AC-008 | TC-033 | integration | 验证任务包含全部筛选结果 |

- 每条 AC 必须至少映射一个直接实现其行为的任务和一个测试用例；无法自动化时，必须在规格的“覆盖缺口”中记录原因、替代验证方式和评审结论。
- 直接实现验收行为的任务必须声明其覆盖的 AC；准备、共享基础设施、纯文档及其他不直接实现验收行为的任务可以标记为“AC：不适用”，但必须说明理由。
- 每个测试用例必须在名称、注释或元数据中引用其验证的 `AC-xxx`。验证验收行为的测试任务或测试用例不得缺少 AC 归属；不直接验证验收行为的测试辅助任务必须标记为“AC：不适用”并说明理由。
- 一个测试用例覆盖多条 AC 时，必须逐条列出对应 AC，并对每条 AC 保留独立、可判定的断言；不能以“测试整个功能”替代具体映射。

## 追踪完整性门禁

测试先行检查和提交前检查必须同时验证以下缺口：

1. 未映射到实现任务的 AC。
2. 未映射到测试用例的 AC。
3. 直接实现验收行为但未声明 AC 归属的任务。
4. 验证验收行为但未声明 AC 归属的测试任务或测试用例。
5. 仅有部分断言覆盖的复合 AC。
6. 标记“AC：不适用”但未说明理由，或实际直接实现、验证验收行为的任务被错误标记为“不适用”。

发现缺口时，在实现前记录为覆盖缺口，并由评审人明确豁免、替代验证方式和后续补齐责任；不得通过删除、合并或降低 AC 可判定性来掩盖缺口。
