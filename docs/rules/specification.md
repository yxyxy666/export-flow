# 规格准备与设计草稿规则

## 适用范围与归属

每次创建或修订功能规格均遵守本规则。是否需要启动规格流程，仍由
[`AGENTS.md`](../../AGENTS.md) 和[项目宪法](../../.specify/memory/constitution.md) 的风险分级决定；
本规则不要求纯讨论或纯文档变更生成功能规格。

`spec.md` 定义需求和范围；`plan.md` 承载结构与函数设计；`tasks.md` 承载执行顺序、追踪映射、
测试进度和审批记录。使用[标准模板](../../.specify/templates/)，不另建核心规格体系。
测试阶段完成条件遵循[测试规则](testing.md)，具体工具链仍遵循对应工程规则。

## 准备顺序

1. 阅读治理文件、产品与验收基线、适用工程规则和已接受 ADR；核对已有结构及本次风险。
2. 在 `spec.md` 明确用户故事、本期交付、非目标、已确认前提和待确认事项。
3. 在 `plan.md` 设计模块边界、目录、文件、函数与调用链；接口、实体与消息涉及跨边界时同步到相应附属产物。
4. 在 `tasks.md` 将函数与文件设计关联到实现任务，将行为映射到测试，并初始化进度和审批表。
5. 提交三份核心文档及其相关附属产物，等待项目负责人明确批准。此时不编写测试代码或生产代码。

没有已确认依据的选项标为候选并登记到[待确认决策](../decisions-pending.md)，不得为了补齐设计草稿伪造已接受选型。

## 目录与逐文件设计（必填）

`plan.md` 必须给出本次变更范围的完整目录树，包括生产、测试、配置和资源文件；标明新增、修改、
复用或本期仅设计的内容。已有工程只列本次涉及的结构，引用已有公共模块，不要求重写无关功能。

目录树之后按文件列出职责、所属层、主要内容及对应任务。前端、后端和公共模块分别明确边界，
公共模块只收纳有明确调用方、符合既定架构的复用能力，不能提前建立无边界的通用工具集。

配置、类型、枚举、样式、SQL 和静态资源文件须写明内容或字段；确实没有函数的文件注明“无函数”及原因。
测试文件须列计划用例、测试编号和目标行为，不在规格阶段写可执行测试。

## 函数设计草稿（必填）

本次计划新增或修改的自有函数、方法、组件、Hook、用例和端口方法必须逐项列出；复用函数说明来源和调用位置。
每项至少包含：

| 字段 | 要求 |
| --- | --- |
| 所在文件与名称 | 仓库相对路径、函数或方法名；命名遵循[命名规则](naming.md) |
| 参数 | 参数名、类型、必填或可选、默认值及关键约束；无参数须明确标注 |
| 返回值 | 返回类型、异步方式、关键结果与可能错误；无返回值须明确标注 |
| 中文注释草稿 | 简短说明作用、目的及重要边界，可作为后续代码注释的依据 |
| 简短流程 | 用文字描述校验、分支、状态或事务边界与输出，不写具体实现代码 |
| 调用关系 | 列明调用的自有函数或端口、必要的框架 API；无调用时明确标注 |
| 阶段与追踪 | 本期实现或后续设计、实现任务、相关测试；具体验收编号使用可点击链接 |

签名中的自有类型须在同一计划、数据模型或契约中有定义。复杂链路另外列出调用顺序及失败出口，
不能只给函数列表却省略函数之间的协作。未确定事项明确留待审批，不能用空泛描述替代关键判断。

框架生成的方法、依赖库内部函数和没有行为变化的机械访问器无需逐个展开，但须说明省略范围。
详细清单较长时可放入 `function-design.md` 等附属文件，由 `plan.md` 直接链接，内容仍随核心规格一并评审。
该文件只有确有拆分需要时生成，不能成为遗漏 `plan.md` 内容的理由。

## 审批与变更

规格审批和测试先行阶段审批是两次独立门禁，均由项目负责人明确给出结论；`tasks.md` 记录范围、
版本或提交标识、日期和结论。默认覆盖整个功能；按批次执行时必须先明确各批次边界，每批次分别获得所需审批。

规格获批后允许生成测试代码、准备并运行测试；测试环境正常、用例完整、新增行为有预期失败证据等
[测试阶段门禁](testing.md#测试先行阶段与审批) 通过，且再次获项目负责人明确批准后，才实施生产代码。
需求、公开签名、调用边界或验收范围实质变化时先同步规格、计划、任务与相关契约，并重新确认受影响范围的审批。
纯文字修正不自动撤销无关审批；新行为的测试必须先行，旧审批不得覆盖新增范围。
