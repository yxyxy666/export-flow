# 前端工程规则

## 1. 文档定位

本文定义 Export Flow 前端的架构边界、路由、状态、接口协作、交互、质量和安全规则，供功能规格、实现与评审共同使用。

- 上游产品基线：[`docs/product/order-export-prd.md`](../product/order-export-prd.md) `1.0.2`。
- 治理依据：[`AGENTS.md`](../../AGENTS.md) 与 [`.specify/memory/constitution.md`](../../.specify/memory/constitution.md)。
- 相关规则：[`naming.md`](naming.md)、[`testing.md`](testing.md)、[`build.md`](build.md)。
- 技术决策：[`ADR-0002 前端技术栈与测试范围`](../adr/0002-frontend-stack-and-test-scope.md)。
- 文档状态：第一版草案。标记为“待确认”的内容在转为 ADR 或从待决策清单移除前，不得视为既定技术选型。

本文只定义跨功能、长期有效的前端规则。单次功能的页面细节、验收标准、接口契约和测试映射应写入对应的 `specs/<feature-dir>/`。

本期定位为本地学习项目，使用合成数据，不建设登录、认证授权、权限审计、生产监控和合规流程。保留输入校验、错误处理和测试先行等基本工程规则；学习项目定位不豁免既有 SDD/TDD 门禁。

## 2. 已确认的产品约束

前端设计必须保持以下产品行为，不得以实现便利改变：

- 仅提供“订单管理”和“导出任务”两个业务页面；订单管理只包含 PRD 中的查询、选择和导出，不包含增删改。
- 订单查询使用全部已填写条件的“并且”关系；查询和修改每页数量后回到第一页。
- 勾选订单跨分页保留；只有修改筛选条件并重新查询或执行重置时才清空。
- 支持“导出已选”和“导出筛选结果”，导出配置默认选择全部九个业务字段且至少保留一个字段。
- 创建导出任务是异步操作，不在订单列表请求中等待或直接返回文件。
- 任务状态为 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`；前端只展示后端返回的状态，不自行推导最终状态。
- 只有成功任务可以下载，只有失败任务可以重试；禁用操作必须说明原因。
- 未知订单状态或销售渠道统一显示“未知”，不得直接把未知协议值作为用户文案展示。
- 页面、Excel 和文件名统一使用 `Asia/Hong_Kong` 时区；页面日期时间按 `yyyy-MM-dd HH:mm:ss` 展示。
- 用户刷新或离开页面不影响后台任务；本期不提供离开页面后的完成通知。
- 本期页面与文件中的客户姓名、手机号按原值展示。该产品决定不等于允许写入日志、监控事件或持久化浏览器存储。

## 3. 架构与职责边界

前端采用以下逻辑分层；实际目录名可随框架调整，但依赖方向不得反转：

```text
页面与路由 -> 功能用例/状态 -> 领域模型与规则
                         -> API client -> 服务端契约
```

- 页面和组件负责展示、输入、键盘/鼠标交互及调用用例，不直接拼装请求 URL、鉴权头或协议 DTO。
- 功能用例层负责查询、分页、跨页选择、导出配置、创建任务、轮询、下载和重试等流程编排。
- 领域层保存与框架无关的值对象、枚举映射、校验及状态动作规则，并可通过单元测试独立验证。
- API client 集中处理基础地址、超时、取消、鉴权、协议序列化、错误归一化和响应解析。
- DTO 与页面 ViewModel 分离；协议字段变化只能在 API client/mapper 边界扩散。
- 通用 UI 状态与业务状态分离，不把服务端数据复制到多个全局 store。
- 不在组件、路由守卫或通用拦截器中静默实现业务规则。

## 4. 技术栈选择规则

前端使用 React + TypeScript + Vite，包管理器使用 `pnpm`，UI 组件库使用 Ant Design（简称 `antd`）。路由、服务端状态和表单分别使用 React Router、TanStack Query、React Hook Form + Zod；测试使用 Vitest + Testing Library + MSW。Node.js 最低使用 22 LTS，各依赖在项目初始化时选择相互兼容的稳定版本并由锁文件固定。完整决策见 [`ADR-0002`](../adr/0002-frontend-stack-and-test-scope.md)。

选型必须满足：

- 使用 TypeScript 严格检查 API DTO、领域模型和组件输入。
- 支持声明式路由、路由级懒加载、查询参数解析和未匹配路由处理。
- 服务端状态工具必须支持请求取消、缓存失效、轮询和防止旧响应覆盖新状态。
- 表单方案必须支持跨字段校验，以覆盖时间范围和金额范围规则。
- 表格组件必须支持服务端分页、跨页选择、固定列标识和可访问的禁用原因。
- 所选依赖必须活跃维护、锁定版本、许可兼容，并避免为单一简单功能引入大型运行时依赖。
- 生产环境不得依赖浏览器中的密钥；环境差异通过构建配置或运行时公开配置注入。

### 4.1 Ant Design 使用规则

- 表单、输入框、选择器、日期时间选择器、按钮、表格、分页、对话框、提示、进度、空状态和结果页等通用 UI 必须优先使用 Ant Design 组件，不重复实现同类基础控件。
- 业务组件可以组合和封装 Ant Design 组件，但不得复制其内部实现或绕过统一主题。
- 样式通过 Ant Design 设计令牌、组件属性和局部样式扩展；不得大范围覆盖内部类名或依赖不稳定的 DOM 结构。
- Ant Design 没有满足需求的组件时才允许自定义，并保持键盘、焦点、禁用状态和视觉规范与现有组件一致。
- 404 使用 Ant Design `Result` 组件；表单、表格和状态提示也遵循本节统一规则。
- Ant Design 的具体版本、图标包、日期库和主题令牌在项目初始化时锁定。

项目明确不建设端到端测试；关键行为由单元、组件、前端集成和契约测试覆盖。

## 5. 路由设计

### 5.1 路由原则

- 每个主要视图必须具有可直接访问和刷新的稳定 URL。
- 查询条件、状态、页码和每页数量进入 URL query，便于刷新、分享和返回；跨页勾选和未提交表单不进入 URL。
- URL 表达已提交查询快照，不是编辑中的筛选表单。查询提交时更新筛选参数，分页操作只更新页码和每页数量。
- 路由进入时必须解析、校验并规范化 query；非法枚举、数字或日期不得直接进入 API 请求。
- 浏览器后退/前进应恢复 URL 对应的已提交查询和分页，不恢复敏感信息或跨页勾选。
- 未匹配路由使用 Ant Design `Result` 展示轻量 404 兜底视图，提供“返回订单管理”入口；不计为新增业务页面。接口错误在原页面处理，渲染异常使用错误边界恢复视图，不额外建立 500、403 或登录路由。

### 5.2 业务页面与 URL

应用部署在站点根路径，仅提供两个业务页面，不设置任务详情路由。

| 路由 ID | URL | 用途 | 主要 query |
| --- | --- | --- | --- |
| `orders` | `/orders` | 订单管理：筛选、分页、勾选和发起导出 | `orderNo`、`status`、`channel`、`orderedFrom`、`orderedTo`、`minAmount`、`maxAmount`、`page`、`pageSize` |
| `exportTasks` | `/export-tasks` | 按状态查看任务进度、下载及重试 | `status`、`page`、`pageSize` |
| `notFound` | `*` | 未匹配路由 | 无 |

首版不为导出配置和失败原因建立独立路由：导出配置是订单管理内的短流程，失败摘要直接在任务列表或可访问的详情弹层展示。

默认入口 `/` 重定向到 `/orders`，主导航提供“订单管理”和“导出任务”两个入口。

## 6. 页面与交互状态

### 6.1 状态所有权

| 状态 | 所有者 | 持久化策略 |
| --- | --- | --- |
| 编辑中的筛选值 | 页面表单 | 仅内存，不自动触发查询 |
| 已提交查询快照、状态筛选与分页 | React Router query | 刷新和前进/后退可恢复 |
| 订单、总数、导出任务 | 服务端状态缓存 | 按查询键缓存，不写长期浏览器存储 |
| 跨页已选订单 ID | 订单列表功能状态 | 页面会话内存；修改条件并查询或重置时清空 |
| 导出字段与范围 | 导出配置状态 | 弹层关闭后清除；每次打开默认九个字段全选 |
| 创建请求幂等键 | 单次提交状态 | 同一次逻辑提交及其安全重试复用；新建或主动重试任务时生成新键 |

筛选表单必须区分 `draftFilters` 与 `submittedFilters`。用户编辑字段但尚未点击“查询”时，已有结果、选择和“导出筛选结果”仍对应 `submittedFilters`；界面不得把未提交条件误传给导出接口。

首次进入订单管理页面时立即按无筛选条件查询第一页。创建任务成功后清空订单选择并进入导出任务页面；创建失败时保留筛选条件、导出字段和订单选择。

### 6.2 异步状态

每个异步区域明确区分 `idle`、`loading`、`empty`、`error`、`success`，并遵守：

- 首次加载和后台刷新分开表达，后台刷新不得清空已有可用数据或造成明显闪烁。
- 新查询取消旧请求，或通过请求标识忽略旧响应，防止过期结果覆盖新条件。
- 提交按钮在请求进行中防重复触发，但幂等性仍由服务端保证。
- 页面卸载时停止无意义的前端轮询和更新，不取消已经由服务端接受的导出任务。
- 错误状态提供与当前操作相关的重试入口；表单校验错误聚焦到首个错误字段。

### 6.3 订单选择

- 使用稳定且唯一的订单 ID 作为选择键，不使用表格行号或订单号的展示文本。
- “全选当前页”只影响当前页记录，不得被表达为“选择全部筛选结果”。
- 已选择数量以选择集合为准，并在跨页后持续可见。
- 重置必须原子地恢复空筛选、第一页、默认每页 20 条并清空选择，然后立即查询无筛选条件的第一页。

### 6.4 任务进度

- `PENDING` 显示 `0 / N`；`RUNNING` 同时显示已处理数、总数和百分比；百分比由有效数值计算并限制在 0 到 100。
- 若服务端暂时无法提供有效总数，不伪造百分比，应显示不确定进度并记录契约异常。
- 导出任务页面可见时每 3 秒刷新当前列表，不以当前页存在活跃任务为前提，避免漏掉新任务或其他页的变化。离开页面或切后台时暂停，重新进入或恢复可见时立即刷新。
- 同一任务的后到旧响应不得覆盖较新的进度或终态。终态一旦观察到，不再由前端改回非终态。
- 请求未结束时跳过下一轮，避免重叠请求；轮询失败保留已有数据并显示错误，下一个周期重试，不实现指数退避。
- 任务状态筛选包含全部、`PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`；切换状态后返回第一页，“全部”不提交状态条件。
- 任务列表使用服务端分页，默认每页 20 条，可选 20、50、100；修改每页数量后返回第一页。
- 普通轮询保留当前页；重试成功创建新任务后返回第一页。任务按创建时间倒序、再按任务唯一 ID 倒序稳定排列。

## 7. 表单、展示与数据规则

- 前端在发起请求前校验开始时间不晚于结束时间、最小金额不大于最大金额。
- 订单号使用精确匹配。时间和金额范围均包含开始/结束或最小/最大边界。
- 下单时间使用 Ant Design 秒级日期时间范围控件；按 `Asia/Hong_Kong` 输入和展示，提交前转换为 UTC，控件及序列化不得丢失秒。
- 首版合成订单仅使用 `CNY`，金额保留两位小数；输入和 DTO 使用十进制定点字符串，不使用二进制浮点进行业务计算。
- 接口时间统一使用 UTC ISO 8601 字符串（带 `Z`），例如 `2026-09-18T04:30:00Z`。前端将按 `Asia/Hong_Kong` 输入的时间转换为 UTC 后请求，并将接口 UTC 时间转换为 `Asia/Hong_Kong` 后用于页面、Excel 和文件名展示。
- 协议枚举在领域层做穷尽映射，并为未知值提供“未知”兜底和非敏感诊断事件。
- 文件大小使用一致的单位规则并提供完整值；空结束时间和空文件大小显示统一占位符。
- 导出字段使用稳定字段 ID，不以中文表头作为协议值；请求必须显式提交有序字段列表，首版按产品定义的九个业务字段顺序保留用户勾选的字段。
- 服务端返回的文件名必须经过安全解析；不得把未经处理的响应头内容写入 DOM。
- 订单列表按下单时间倒序、再按订单唯一 ID 倒序稳定排列。

## 8. 接口协作规则

### 8.1 契约边界

- API 使用 JSON REST，路径前缀为 `/api/v1`，使用 OpenAPI 维护机器可读契约；功能规格的 `contracts/` 必须引用或包含对应契约。
- 前端不得根据当前页面数据自行判断导出总量是否合法；服务端必须重新校验范围和 200,000 条上限。
- 创建任务请求必须携带 `Idempotency-Key`。网络超时后重试同一次提交时复用原键；用户明确发起新导出或对失败任务执行重试时使用新键。
- 订单查询、任务查询和创建响应必须携带前端完成页面展示所需的稳定 ID、计数与状态，不依赖额外逐行请求。
- 错误响应至少包含稳定的 `code`、用户可安全展示或映射的 `message`、可选字段错误和可检索的 `requestId`；前端逻辑只依赖 `code`，不依赖文案。
- API client 必须设置超时并支持取消。只对明确安全的读请求和使用相同幂等键的创建请求进行受控重试。
- 列表分页、排序、筛选语义和最大页大小由契约明确；前端不得依赖数据库或服务端的隐式默认顺序。
- 本期下载接口不要求鉴权，但必须校验任务状态并处理文件不存在、网络失败等错误。

### 8.2 REST 契约基线

以下路径作为功能规格编写详细 OpenAPI 契约的基线：

| 操作 | 方法与路径 | 前端关注的请求/响应 |
| --- | --- | --- |
| 查询订单 | `GET /api/v1/orders` | query 为已提交筛选及 `page`、`pageSize`；响应含 `items`、`page`、`pageSize`、`total` |
| 创建导出任务 | `POST /api/v1/export-tasks` | header 含 `Idempotency-Key`；body 含范围快照与有序 `fields`；响应含完整任务摘要 |
| 查询导出任务 | `GET /api/v1/export-tasks` | 支持分页；响应含任务摘要列表和总数 |
| 下载结果 | `GET /api/v1/export-tasks/{taskId}/file` | 成功返回文件流及安全文件名；非成功任务返回结构化错误 |
| 重试失败任务 | `POST /api/v1/export-tasks/{taskId}/retries` | header 使用新的 `Idempotency-Key`；响应为新任务摘要，原任务不变 |

创建任务使用显式判别联合：`scope.type = SELECTED` 时提交不可变的 `orderIds`；`scope.type = FILTERED` 时提交与已提交查询完全一致的 `filters`。两种范围不得同时出现，分页参数不得进入筛选结果导出的范围快照。

初始化后的合成订单数据只读；失败任务重试时复用原任务的范围和有序字段配置，创建新任务且不修改原任务。

所有列表接口使用从 1 开始的 `page`，与用户界面一致。

### 8.3 文件下载

- 下载前根据最新任务状态决定操作是否可用，服务端仍必须校验状态。
- 使用同源直接下载链接 `GET /api/v1/export-tasks/{taskId}/file`，由服务端返回文件流、`Content-Type` 和安全的 `Content-Disposition` 文件名；不使用 Blob、中转页面或签名 URL。
- 点击下载前以前端已知任务状态控制按钮；服务端再次校验任务状态。直接链接返回错误时由浏览器显示响应，本期不额外解析结构化下载错误。

## 9. 基本错误处理

- 用户可见错误不得泄露堆栈、SQL、内部地址、令牌、客户姓名或手机号。
- 使用合成测试数据，不引入真实个人信息或凭证；无需搭建生产监控、分析事件或隐私评审流程。
- 捕获渲染异常并提供页面级恢复入口；普通接口失败留在当前区域展示并可重试。
- 资源不存在、幂等冲突、校验失败和服务不可用应可区分，不统一显示为“网络错误”。

## 10. 可访问性、响应式与兼容性

- 使用语义化表单、表格、对话框和按钮；交互控件支持键盘、可见焦点及可读名称。
- 禁用操作必须同时提供可被键盘和读屏用户获取的原因；不得只依赖 hover tooltip。
- 打开对话框后移动焦点，关闭后将焦点还给触发控件；校验错误与对应字段建立程序化关联。
- 状态不能只靠颜色表达；任务进度更新使用不过度打扰的可访问通知策略。
- 响应式布局不得依赖固定视口宽度。窄屏可对表格横向滚动，但主要操作和行上下文必须保持可理解。
- 界面仅提供简体中文，定位桌面浏览器，按最小视口 1280×720 验证。支持最新两个稳定版本的 Chrome、Edge、Firefox 及当前稳定 Safari，不依赖无降级方案的实验性 API。

## 11. 性能规则

- 主要路由按页面拆包，导出配置等非首屏能力按需加载。
- 订单和任务列表只请求当前页；不得在浏览器中加载全部匹配订单来完成分页或筛选结果导出。
- 查询输入不因每次按键自动请求；由用户提交查询。重复的相同读请求应合并或复用缓存。
- 表格渲染应以每页最多 100 行为基准，避免每行创建不必要的全局订阅或昂贵格式化器。
- 轮询请求不得重叠；上一次未完成时不再启动同类请求。
- 本期不设置前端性能预算或生产监控；若后续扩展范围，再通过 ADR 补充指标和工具。

## 12. 前端测试与质量门禁

测试遵守 [`testing.md`](testing.md) 的 AC、任务和测试双向追踪规则。涉及行为变化时先写失败测试或记录覆盖缺口，再实现。

- 单元测试：范围校验、query 解析、金额/时间格式化、枚举兜底、状态动作、进度计算和 DTO 映射。
- 组件测试：筛选表单、跨页选择、导出字段至少保留一个、禁用原因、loading/empty/error/success 和可访问性。
- API 集成测试：查询参数序列化、错误归一化、取消与旧响应、幂等键复用、轮询停止和下载错误。
- 契约测试：枚举、分页、错误体、任务状态和文件下载头；前后端契约变更必须在 CI 中暴露不兼容。

前端 CI 至少执行格式化检查、静态分析、类型检查、单元/组件/前端集成测试和构建，并遵守 [`build.md`](build.md) 的总体顺序。本期不设置端到端测试门禁；具体命令和覆盖率在项目初始化后补充。

## 13. 目录与命名

采用以下职责目录；项目初始化时可以在不改变职责边界的前提下确定具体源码根路径：

```text
app/        应用入口、路由、全局 provider
pages/      路由页面
features/   orders、export-tasks 等业务用例与组件
domain/     领域类型、规则和格式化
api/        DTO、client、mapper 和错误模型
shared/     无业务归属的 UI 与工具
```

- 功能模块按业务能力命名，不建立无边界的 `utils`、`services` 或 `components` 大目录。
- 文件、变量、函数和协议字段遵守 [`naming.md`](naming.md)；中文只用于用户文案和中文维护文档。
- 单元、组件和前端集成测试与被测模块就近放置或采用统一测试目录，二者择一后不得混用。
- 仅由单一功能使用的组件留在该功能内；至少被两个无直接业务依赖的功能稳定复用后才提升到 `shared/`。

## 14. 变更与评审检查

前端规格或实现评审至少检查：

1. 产品 AC 是否映射到实现任务和测试，且与本规则无冲突。
2. 编辑中筛选、已提交筛选、分页和跨页选择是否边界清楚。
3. 请求是否可取消或防旧响应，创建操作是否正确使用幂等键。
4. 四种任务状态、所有禁用动作及错误分支是否均有可观察表现。
5. DTO 是否在边界转换，组件是否绕过 API client 或承载业务规则。
6. URL、缓存、日志和监控是否可能泄露个人信息或凭证。
7. 键盘、焦点、读屏、窄屏和浏览器兼容是否经过验证。
8. 新增依赖、路由、公共组件或契约是否同步文档和 ADR。
